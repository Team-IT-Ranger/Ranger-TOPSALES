**คำถามทั้ง 4 ข้อท้ายเอกสารเจ้าของระบบตัดสินแล้ว 27 ก.ย. 2026** — ดูหัวข้อ 8

# 1. ปัญหาของโครงสร้างเดิม

ชุดราคาผูกกับกลุ่มลูกค้า **ช่องเดียว** (`price_lists.customer_group_id`)

```
price_lists.customer_group_id = 2   →  ลูกค้าที่ customers.group_id = 2 เท่านั้นที่ได้ราคานี้
```

ข้อจำกัดที่ตามมา:

| อยากได้ | ทำได้ไหมกับของเดิม |
|---|---|
| ราคาเฉพาะช่องทางค้าส่ง | ❌ ต้องสร้างกลุ่มลูกค้าปลอม "ค้าส่ง" แล้วย้ายร้านเข้า |
| ราคาเฉพาะเขตตะวันออก | ❌ เหมือนกัน |
| ราคาเฉพาะร้านที่ซื้อเชื่อ | ❌ เหมือนกัน |
| ร้านที่เป็นทั้ง "ค้าส่ง" และ "ตะวันออก" | ❌ **ทำไม่ได้เลย** — ร้านอยู่ได้กลุ่มเดียว |
| ราคาเฉพาะรายชื่อ 5 ร้านที่เจรจาไว้ | ❌ ต้องสร้างกลุ่มให้ 5 ร้านนั้น แล้วร้านหลุดจากกลุ่มเดิม |

ปมอยู่ที่ **"กลุ่มลูกค้า" ถูกใช้ทำสองหน้าที่พร้อมกัน** — ทั้งเป็นการจัดหมวดร้าน และเป็นกุญแจเข้าถึงราคา
พอสองเรื่องนี้ไม่ตรงกันเมื่อไหร่ ก็ต้องบิดข้อมูลร้านให้เข้ากับราคา ซึ่งทำให้รายงานตามหมวดผิดตามไปด้วย

# 2. ห้าชั้นของราคาและส่วนลด

แยกให้ขาดว่าแต่ละชั้นตอบคำถามอะไร จะได้ไม่เอาไปปนกัน

```
ชั้น A  การจ่ายชุด      ตัวแทนรายนี้ "ได้รับชุดไหนมาใช้"             ✅ ทำแล้ว (ของใหม่ 27 ก.ย.)
ชั้น 0  สิทธิ์เข้าถึง    ร้านนี้ "ได้ชุดราคาไหน"                    ✅ ทำแล้ว (ของใหม่)
ชั้น 1  ราคาต่อหน่วย    ซื้อเท่านี้ หน่วยนี้ จ่ายเชื่อ/สด ราคาเท่าไร   ✅ มีอยู่แล้ว
ชั้น 2  ส่วนลดรายบรรทัด ลดเฉพาะสินค้าตัวนี้อีกกี่ %                  ❌ ตัดสินแล้วว่าไม่ทำ
ชั้น 3  ส่วนลดท้ายบิล   ซื้อครบเท่านี้ ลดทั้งบิลอีกกี่ %              ✅ มีอยู่แล้ว
ชั้น 4  ของแถม          ซื้อครบเท่านี้ แถมอะไร                       ⬜ ยังไม่ทำ (เจ้าของระบบสั่งพักไว้)
```

**ชั้น A กับชั้น 0 ไม่ใช่เรื่องเดียวกัน อย่ายุบรวม** — ชั้น A คือ "บริษัท**มอบ**ชุดนี้ให้ตัวแทนรายไหน"
ชั้น 0 คือ "ภายในตัวแทนนั้น ร้านแบบไหน**ได้ใช้**" · เขียนกฎชั้น 0 ว่า `ตัวแทน = BDC` ก็พอทำให้ราคาถูกต้องได้
แต่ตอบไม่ได้ว่า "ตัวแทน BDC มีชุดอะไรอยู่บ้าง" โดยไม่ไล่ลูกค้าทีละราย ซึ่งเป็นคำถามที่หน้าจอจ่ายงาน
รายงาน และฝั่งตัวแทนต้องการ · **ต้องผ่านทั้งสองชั้น**

**กติกาที่ต้องคงไว้**: ร้านที่เข้าเงื่อนไขชุดราคา จะใช้ชุดราคานั้นเป็น**แหล่งราคาเดียว**
ไม่ซ้อนกับ `discount_rules` แบบเดิม (ไม่งั้นส่วนลดเบิ้ล) · สินค้าที่ไม่อยู่ในชุดราคา = ขายให้ร้านนั้นไม่ได้
ซึ่งดีกว่าปล่อยให้ขายผิดราคา

# 3. ชั้น 0 — สิทธิ์เข้าถึงชุดราคา ✅

## 3.1 โครงสร้าง

```
price_list_rules             1 แถว = 1 "กลุ่มเป้าหมาย" ของชุดราคานั้น
  price_list_id, name, match_type(all|any), priority, is_active, note

price_list_rule_conditions   1 แถว = 1 เงื่อนไข
  rule_id, field, op, value
```

**หนึ่งชุดราคามีได้หลายกฎ** เพราะชุดเดียวมักขายให้หลายกลุ่มที่นิยามคนละแบบ
เช่น "ซุปเปอร์ชีป" = ช่องทาง `SC` **หรือ** รหัสกลุ่มเดิม `SV02` — ถ้าบังคับเป็นก้อนเดียว
ต้องเขียน OR ซ้อน AND ซึ่งคนตั้งค่าอ่านไม่ออกและตั้งผิดง่าย

## 3.2 คุณลักษณะที่ใช้ตั้งเงื่อนไขได้

กลุ่มลูกค้า · ประเภทร้าน/ช่องทาง · เขต/สายวิ่ง · รูปแบบการขาย · การชำระเงิน · จังหวัด · อำเภอ ·
รหัสไปรษณีย์ · สถานะภาษี · รหัสลูกค้า · พนักงานขายประจำร้าน · ตัวแทนจำหน่าย · สถานะ · ชื่อร้าน
· และ **`attr:<key>`** ที่ไปอ่าน `customers.attributes` (JSON)

> `attr:` สำคัญกับข้อมูลที่เพิ่งยกมาจากระบบเดิม — ร้าน 2,039 รายของ BDC ยังถือรหัสกลุ่มเดิม
> `SV01`–`SV12` อยู่ใน `attributes.sourceGroupCode` ตั้งกฎอ้างรหัสนั้นได้เลย **โดยไม่ต้องรอ map เข้ากลุ่มลูกค้าก่อน**

**เป็น whitelist โดยตั้งใจ** — เปิดให้พิมพ์ชื่อคอลัมน์อะไรก็ได้ เท่ากับพิมพ์ผิดแล้วกฎเงียบ
ไม่มีใครรู้ว่าทำไมร้านไม่เข้าเงื่อนไข ระบบจึงปฏิเสธชื่อที่ไม่รู้จักตั้งแต่ตอนบันทึก

ตัวดำเนินการ: `eq` `ne` `in` `notin` `contains` `startswith` `gte` `lte` `empty` `notempty`
(เทียบแบบไม่สนตัวพิมพ์และตัดช่องว่างหัวท้าย — ข้อมูลนำเข้ามักมีช่องว่างติดมา)

## 3.3 ลำดับการตัดสิน

```
1. คัดเฉพาะชุดที่ status = active และวันที่อยู่ในช่วง
2. ชุดไหน "เข้าเงื่อนไข" = มีกฎข้อใดข้อหนึ่งผ่าน (คะแนนของชุด = priority ของกฎที่ผ่านและสูงสุด)
3. เลือกชุดที่ priority สูงสุด
4. เท่ากัน → valid_from ใหม่กว่าชนะ → เท่ากันอีก → record_id สูงกว่าชนะ
```

**ต้องมีตัวตัดสินครบทุกชั้น** ไม่งั้นวันที่มีสองชุดคะแนนเท่ากัน ผลจะสลับไปมาตามลำดับแถวในชีต
= ลูกค้าคนเดียวกันได้คนละราคาในสองคำขอติดกัน ซึ่งเป็นบั๊กที่หาสาเหตุยากที่สุดแบบหนึ่ง

**เข้ากันได้กับของเดิม**: ชุดที่ยังไม่มีกฎแต่มี `customer_group_id` ถือว่ามีกฎซ่อน
"กลุ่มลูกค้า = ค่านั้น" ลำดับ **0** → ชุดราคา 4 ชุดที่เปิดใช้อยู่บน prod ทำงานเหมือนเดิมทุกประการ
และกฎใหม่ที่ตั้ง priority > 0 จะชนะได้เสมอเมื่อตั้งใจให้ชนะ

**กฎที่ไม่มีเงื่อนไขเลย = ไม่ผ่าน** (ไม่ใช่ผ่านทุกคน) — กฎว่างมักเกิดจากตั้งค้างไว้
ถ้าตีความว่าครอบคลุมทุกร้าน ชุดนั้นจะไปทับราคาของทุกคนโดยไม่มีใครตั้งใจ

## 3.4 เครื่องมือช่วยตั้งค่า ✅

| เครื่องมือ | ตอบคำถาม |
|---|---|
| `previewPriceListAudience` | "กฎนี้จะครอบคลุมร้านกี่ร้าน ร้านไหนบ้าง" — **ดูก่อนกดใช้จริงเสมอ** |
| `explainCustomerPricing` | "ทำไมร้านนี้ได้ราคานี้" — บอกชุดที่ชนะ เหตุผล และชุดที่แข่งอยู่พร้อมเหตุที่ใช้ไม่ได้ |

สองตัวนี้คือหัวใจ กฎที่กว้างเกินไปจะไปทับราคาของร้านที่ไม่ได้ตั้งใจ
และกว่าจะรู้ก็ตอนออกบิลผิดราคาไปแล้ว

# 4. ชั้น 1 — ราคาต่อหน่วย ✅ (ของเดิม ไม่แตะ)

- ขั้นบันไดนับ**จำนวนลังรวมของสินค้าที่ใช้ `line_id` เดียวกัน** (กลิ่นต่างกันแต่เป็นสินค้าเดียวกัน นับรวม)
- ราคาที่เก็บเป็น**ราคารวม VAT** แยกคอลัมน์เงินสด/เครดิต เลือกตามวิธีชำระตอนขาย
- `PK` (แพ็ค) ขายได้เฉพาะ Cash Van + เงินสด — บังคับฝั่งเซิร์ฟเวอร์ (`PACK_VAN_ONLY` / `PACK_CASH_ONLY`)

# 5. ชั้น 3 — ส่วนลดท้ายบิล ✅ + ที่เสนอปรับ 🟡

ตอนนี้: `price_list_bill_promos` = ยอดรวมไม่รวม VAT ครบขั้นไหน ลดทั้งบิล % นั้น (ใช้ขั้นสูงสุดที่ถึงเพียงขั้นเดียว)
สินค้าที่ติ๊ก `no_discount` ถูกตัดออกจากฐานที่ลดได้แล้ว

❌ **เงื่อนไขนับจำนวนลัง — ตัดสินแล้วว่าไม่ทำ** (27 ก.ย. 2026) ยอดเงินพอแล้ว
เหตุผล: ยอดเงินเป็นตัวเลขที่อยู่บนออร์เดอร์อยู่แล้วและร้านค้าเข้าใจง่ายที่สุด ส่วน "ครบกี่ลัง" ต้องนิยามเพิ่มว่า
นับข้ามสินค้าหรือนับแยก และแปลงหน่วยยังไงเมื่อสั่งปนแพ็ค/ชิ้น — ความซับซ้อนไม่คุ้มกับที่ได้

🟡 ที่ยังเปิดไว้ (ยังไม่ทำ ไม่ได้ปฏิเสธ):
- ส่วนลดเป็น**จำนวนเงิน**ไม่ใช่แค่ % (ลด 500 บาทเมื่อซื้อครบ 10,000)
- ส่วนลดที่ผูกกับ**กฎสิทธิ์**เหมือนชั้น 0 (ลูกค้ากลุ่มนี้ได้โปรท้ายบิลเพิ่มอีกชุด)

# 6. ชั้น 2 — ส่วนลดรายบรรทัด ❌ (ข้ามไปก่อน — ตัดสิน 27 ก.ย. 2026)

ยังไม่มี และเป็นช่องว่างที่ใหญ่ที่สุดที่เหลืออยู่ ใบราคาจริงของบริษัทมีเคสแบบ
"ลดเพิ่ม 5% เฉพาะสินค้าตัวนี้ในเดือนนี้" ซึ่งตอนนี้ต้องไปแก้ราคาในชุดราคาแทน
ทำให้ประวัติราคาปกติหายไปและต้องแก้กลับเมื่อจบโปร

🟡 ถ้าจะทำในอนาคต: `price_list_line_promos` — ผูกกับ `price_list_id` + `product_id` หรือ `line_id`
มี `min_qty`, `percent` หรือ `amount`, ช่วงวันที่ของตัวเอง (สั้นกว่าอายุชุดราคาได้)

❌ **ตัดสินแล้วว่ายังไม่ทำ** — ชั้น 1 + ชั้น 3 ครอบคลุมงานส่วนใหญ่ และตอนนี้**แก้ราคาในชุดที่ใช้งานอยู่ได้แล้ว**
(หัวข้อ 4) โปรรายสินค้าสั้นๆ จึงทำด้วยการแก้ราคาขั้นแล้วแก้กลับได้ โดยมี `price_list_change_log` เก็บว่าใครแก้อะไร
ซึ่งเป็นเหตุผลเดิมที่กลัวว่าจะเสียประวัติ — หมดไปแล้ว · ค่อยกลับมาทำเมื่อโปรรายสินค้าเกิดถี่จนการแก้กลับเริ่มพลาด

# 7. ลำดับการคำนวณทั้งหมด (ที่เสนอให้เป็นมาตรฐาน)

```
1. หาชุดราคา                 ← ชั้น 0 (กฎสิทธิ์)
2. ราคาต่อหน่วยตามขั้น        ← ชั้น 1
3. หักส่วนลดรายบรรทัด         ← ชั้น 2 (ตัดสินแล้วว่าไม่ทำ — ข้ามขั้นนี้)
4. รวมเป็นยอดก่อนส่วนลดท้ายบิล
5. หักส่วนลดท้ายบิล           ← ชั้น 3 (ไม่กินรายการ no_discount)
6. ถอด VAT จากยอดสุทธิ        ← แยกของยกเว้นภาษีออกก่อน เฉลี่ยส่วนลดตามสัดส่วน
7. บวกของแถม                 ← ชั้น 4 (ยังไม่ทำ) ไม่กระทบยอดเงิน
```

ข้อ 6 ทำแล้วและมีเทสต์คุม — **ส่วนลดหักก่อนคิด VAT เสมอ** (คิด VAT ก่อนแล้วค่อยหักส่วนลด = VAT เกินจริง)

## 8.1 ร้าน BDC 2,039 ราย — จะ map เข้ากลุ่มไหน

อ่านไฟล์ต้นทาง (`reference/customer_for_bdc.xlsx` ชีต `customer`) แล้วได้ข้อเท็จจริงที่เปลี่ยนคำตอบ:

**`GroupCode` (SV01–SV12) ไม่ใช่กลุ่มราคา แต่เป็นสายวิ่ง** — มันแบ่งตามจังหวัดเป๊ะ:

```
SV11  1,174 ร้าน  →  จังหวัด 20,21,22,23   (ชลบุรี ระยอง จันทบุรี ตราด)      = ตะวันออกฝั่งทะเล
SV12    856 ร้าน  →  จังหวัด 24,25,26,27   (ฉะเชิงเทรา ปราจีนบุรี นครนายก สระแก้ว) = ตะวันออกตอนใน
SV01–SV04  9 ร้าน  →  ร้านค้าส่ง/ซุปเปอร์มาร์เก็ตที่แยกออกมา (กระจายทุกจังหวัด)
```

ทุกจังหวัดที่ BDC ขายอยู่คือ**ภาคตะวันออกทั้งหมด** (มีสระบุรี 1 ร้านเป็นข้อยกเว้นเดียว)
เทียบกับกลุ่มราคาจริง 4 ชุดบน prod ซึ่งแบ่งตามภูมิภาค → **ร้าน BDC เกือบทั้งหมดอยู่กลุ่มเดียวกัน**
คือ "ร้านค้าเหนือ-อีสาน-ตะวันออก-ใต้" ไม่ได้แบ่งเป็น 2 กลุ่มตาม SV11/SV12

ดังนั้นการ map ที่ถูกคือ:

| ข้อมูลเดิม | ไปอยู่ที่ | เหตุผล |
|---|---|---|
| `GroupCode` SV11/SV12 | **`area_code` (สายวิ่ง)** | เป็นเส้นทางเดินรถ ไม่ใช่ระดับราคา — เอาไปตั้งเป็น `group_id` จะทำให้รายงานตามกลุ่มผิด |
| จังหวัด | **`group_id`** ตามภูมิภาค | ตรงกับวิธีที่ใบราคาจริงแบ่งกลุ่มอยู่แล้ว |
| `ShopTypeCode` (PS/MM/WS/SM…) | **`channel_id` (ประเภทร้าน)** | เป็นชนิดร้าน ไม่ใช่ราคา แต่ตั้งเป็นเงื่อนไขในกฎได้ถ้าจะให้ค้าส่งได้ราคาต่าง |

❗ **6 แถวขยะที่นำเข้ามาด้วย** — `CustNo` = SV01/SV02/SV03/SV04/SV11/SV12 ชื่อ "New" ไม่มีที่อยู่ ไม่มีเบอร์
เป็นแถวแม่แบบ "ลูกค้าใหม่" ของแต่ละสายในระบบเดิม ควรปิดใช้งาน (ไม่ลบ — อาจมีบิลเก่าอ้างถึง)

เครื่องมือที่สร้างรองรับเรื่องนี้: **"จัดกลุ่มลูกค้าเป็นชุด"** (หัวข้อ 3.4) — ตั้งเงื่อนไขด้วยตัวสร้างเงื่อนไข
ชุดเดียวกับกฎสิทธิ์ ดูก่อนว่าโดนกี่ร้าน แล้วค่อยกด — ใช้ซ้ำได้ทุกครั้งที่นำเข้าข้อมูลรอบใหม่
ไม่ใช่สคริปต์ครั้งเดียวทิ้ง

## 8.2 ชุดราคากับตัวแทนจำหน่าย

เลือกทางที่**ไม่แตะสคีมา**: ชุดราคายังเป็นของกลาง แต่ตั้งกฎได้ว่า `ตัวแทนจำหน่าย เท่ากับ BDC`
(`tenant_id` อยู่ใน whitelist อยู่แล้ว และลูกค้าทุกแถวมี `tenant_id` เพราะ `buildCustomerFields` เขียนให้เสมอ)

ได้อะไร: ตั้งราคาเฉพาะตัวแทนรายใดรายหนึ่งได้ทันที · ผสมกับเงื่อนไขอื่นได้ (ตัวแทน BDC **และ** ประเภทร้านค้าส่ง)

เสียอะไร — ต้องรู้ไว้: **ตัวแทนตั้งราคาเองไม่ได้** บริษัทเจ้าของสินค้าเป็นคนตั้งให้ทุกราย
ถ้าวันหนึ่งตัวแทนต้องตั้งราคาขายของตัวเอง ต้องกลับมาเพิ่ม `tenant_id` ที่ `price_lists`
พร้อมแยกสิทธิ์รายโมดูลใหม่ทั้งชุด — คนละงานกับที่ทำตอนนี้

# 9. ชั้น A — การจ่ายชุดให้ตัวแทน ✅ (27 ก.ย. 2026)

> กติกาเจ้าของระบบ: "ชุดราคาและโปรโมชั่นที่ส่วนกลางเตรียมไว้ **จะไม่เอาทุกชุดไปโยนให้ตัวแทนแบบเหมารวม**"

ตาราง `package_tenants` — 1 แถว = ชุดนี้จ่ายให้ตัวแทนรายนี้ · ใช้โครงเดียวกันทั้งชุดราคาและโปรโมชั่น
(`package_type` = `price_list` | `promo`)

| กติกา | เหตุผล |
|---|---|
| **ไม่ระบุตัวแทน = ไม่มีใครได้** | ค่าเริ่มต้นแบบ "ทุกคน" คือสิ่งที่ทำให้เกิดการเหมารวมตั้งแต่แรก |
| ชุดที่มีอยู่ก่อนกติกานี้ = เขียนย้อนหลังให้ครบทุกตัวแทน | `migratePackageAssignments()` — ของที่ขายอยู่ต้องไม่สะดุด · รันซ้ำได้ ไม่ทับชุดที่คนเลือกไว้แล้ว |
| **ตัวแทนดูได้อย่างเดียว** | ราคาคุมจากส่วนกลางทั้งหมด — `savePackageTenants` ปฏิเสธ session ที่สังกัดตัวแทน แม้บทบาทจะมีสิทธิ์ edit |
| ตัวแทนว่าง = ตัวแทนบ้าน `HOUSE` | ขายตรงในนามบริษัทก็ต้องได้รับชุดเหมือนกัน ไม่ใช่ได้ทุกชุดโดยอัตโนมัติ |

**หน้าจอ**: การ์ด "จ่ายให้ตัวแทน — ใครได้ใช้ชุดนี้" บนหน้ารายละเอียดชุดราคา (ชิปเลือกตัวแทน) ·
ปุ่ม "จ่ายให้ตัวแทน" และ "สิทธิ์ลูกค้า" บนแต่ละแถวของตารางโปรโมชั่น ·
ชุดที่ยังไม่ได้จ่ายให้ใครขึ้นแถบเหลืองว่า **ยังไม่มีใครได้ใช้** (ไม่งั้นจะเงียบจนพนักงานเปิดบิลไม่ได้หน้าร้าน) ·
`explainCustomerPricing` บอกเหตุผล "ยังไม่ได้จ่ายชุดนี้ให้ตัวแทน X" แยกจากเหตุผลอื่น

**กฎสิทธิ์ (ชั้น 0) ใช้กับโปรโมชั่นได้ด้วยแล้ว** — `price_list_rules.target_type` (`price_list` | `promo`
· ค่าว่าง = `price_list` เพื่อความเข้ากันได้) ตัวสร้างเงื่อนไขและหน้าจอเป็นชุดเดียวกันทั้งสองที่
โปรที่ไม่ตั้งกฎยังใช้ `customer_group_id` ในตัวมันเองตามเดิม

# 10. โปรโมชั่นซ้อนบนชุดราคาได้ ✅ (27 ก.ย. 2026)

**ของเดิม**: ร้านที่กลุ่มมีชุดราคาใช้งานอยู่ ระบบใช้ชุดราคาเป็นแหล่งราคาเดียว `discount_rules` ไม่ถูกเรียกเลย
พอจัดกลุ่มลูกค้าครบทุกร้าน (เช่น BDC 2,031 ร้าน) **โปรโมชั่นทั้งระบบก็เงียบไปเองโดยไม่มีใครรู้**

**ของใหม่**: ชุดราคา = ราคาตั้ง · โปรโมชั่น = ส่วนลดเพิ่ม

```
1. หาชุดราคา                 ← ชั้น A + ชั้น 0
2. ราคาต่อหน่วยตามขั้น        ← ชั้น 1
3. หักโปรโมชั่น               ← discount_rules ที่ผ่านชั้น A + ชั้น 0 ของตัวเอง
4. หักส่วนลดท้ายบิล           ← ชั้น 3
5. ถอด VAT จากยอดสุทธิ
```

สองจุดที่ตัดสินไว้และมีเทสต์คุม:
- **เกณฑ์ขั้นของส่วนลดท้ายบิลวัดจากยอดที่ลูกค้าสั่ง (ก่อนหักโปร)** — ร้านคิดจากยอดที่ตัวเองสั่ง
  ถ้าวัดหลังหักโปร โปรจะกลายเป็นตัวทำให้หลุดขั้นแล้วได้ส่วนลดรวม**น้อยลงกว่าไม่มีโปร** ซึ่งอธิบายกับร้านไม่ได้
- **ฐานที่เอาไปคูณ % หักโปรออกก่อน** — เงินที่ลดไปแล้วจะลดซ้ำบนก้อนเดิมไม่ได้
- สินค้า `no_discount` ไม่ถูกทั้งโปรและส่วนลดท้ายบิล แต่ยังนับเข้าเกณฑ์ขั้นตามเดิม
- ของแถม (`type: free_goods`) **ยังไม่คิดในเส้นทางชุดราคา** — เจ้าของระบบสั่งพักเรื่องของแถมไว้
- `sales_orders.discount` เก็บส่วนลด**รวมทุกชั้น** ให้ `subtotal - discount = total` เสมอ
