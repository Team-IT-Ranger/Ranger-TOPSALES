# แผ่น 04 — ผังระบบ (เส้นทางงานจริง)

เจ็ดเส้นทาง เดินจากต้นถึงปลายทีละขั้น · แต่ละขั้นบอกว่า **ของขยับที่ไหน** และ **เงินขยับที่ไหน**

---

## เส้นที่ 1 — ขาย → จัดส่ง → เอกสาร → เงิน

### 1.1 สายงานสถานะ (`34_sales_status.gs` · `SO_TRANSITIONS`)

```
 draft          ──มือถือกดยืนยัน──▶  confirmed          ──ศูนย์กดรับงาน──▶  accepted
 (ใหม่/ร่าง)                        (รออนุมัติ)                      (อนุมัติ/เตรียมจัดส่ง)
                                                                              │ ศูนย์แจ้งพร้อมส่ง
                                                                              ▼
 completed      ◀──────────────  delivering       ◀──────────────────  ready_to_ship
 (จัดส่งสำเร็จ)                  (กำลังจัดส่ง)                          (พร้อมจัดส่ง)  ★ จุดตัดสต็อก

 ปฏิเสธ = rejected (ตีกลับให้แก้แล้วยืนยันใหม่ ไม่ต้องเปิดใบใหม่) · ยกเลิก = cancelled (ไปได้จากทุกสถานะ)
```

- **ถอยกลับได้หนึ่งขั้น** (กดผิดเป็นเรื่องปกติ) แต่บิลที่ยกเลิกแล้วเปิดคืนไม่ได้
- **★ ห้ามข้ามขั้น** — `confirmed` ไป `completed` ตรงๆ ไม่ได้ เพราะจะข้ามจุดตัดสต็อก
  ของก็ออกไปโดยไม่มีใครหักยอด **แล้วไม่มีอะไรฟ้องเลย**
- `pending_delivery` = ชื่อเดิมของ `confirmed` **ห้ามลบ** บิลเก่าทั้ง UAT/prod ยังเป็นค่านี้
- **สองแกนแยกกัน ห้ามยุบรวม**: การส่งของ (`status`) กับการเงิน (`payment_status`:
  `unpaid` → `partial` → `paid` + `paid_amount`) — ยุบรวมเมื่อไหร่จะตอบไม่ได้ว่า
  "ส่งของแล้วแต่ยังไม่เก็บเงิน" คือสถานะอะไร · ขายสดจากรถเริ่มที่ `paid` เลย
- ทุกการเปลี่ยนเขียน `order_status_log` เสมอ (ไม่ลบ ไม่ทับ)

### 1.2 ★★ จุดตัดสต็อก — มีจุดเดียวต่อรูปแบบการขาย

| รูปแบบ | ตัดที่ไหน | ตัดเมื่อไหร่ |
|---|---|---|
| **ขายจากรถ** (`immediate`) | `van_stock` ของพนักงานคนนั้น | **ตอนบันทึกบิล** (`_cutVanStock`) — ของถึงมือลูกค้าแล้วจริง |
| **สำนักงานจัดส่ง** (`office_delivery`) | `warehouse_stock` | **ตอนเข้า `ready_to_ship`** |

เลือกตัดที่ `ready_to_ship` เพราะของถูกหยิบออกจากชั้นและแพ็คขึ้นรถแล้ว — ถ้ารอตัดตอน
"ส่งของแล้ว" ระบบจะบอกว่ามีของทั้งที่ของนอนอยู่ในกล่อง **แล้วจะมีคนมาขายซ้ำ**

- **`saleStockTaken(order)` = นิยามเดียวของ "ของถูกตัดไปแล้ว"** ทั้งจุดตัดและจุดคืนของอ่านจากตัวนี้
  ย้ายจุดตัดเมื่อไหร่แก้ที่เดียวแล้วขยับพร้อมกัน
- `updateSalesOrderStatus` เทียบค่าก่อน/หลังแล้วขยับสต็อก **เฉพาะตอนค่าเปลี่ยน** — ขั้นถัดไปจึงไม่ตัดซ้ำ
  (บั๊กตัดซ้ำมองไม่เห็นจากหน้าจอเลย)
- ของไม่พอ = **ปฏิเสธทั้งใบ** ไม่ตัดครึ่งๆ กลางๆ
- คลังที่ใช้: ตัวแทน = คลังของตัวเอง · ขายตรง (HOUSE) = คลังกลาง (`_saleStockScope`)

### 1.3 รอบจัดส่ง — ของไม่พอส่งในรอบเดียว (`48_delivery_rounds.gs`)

```
บิล 1 ใบ  ──▶ รอบ 1 (ส่งเท่าที่มี)  ──▶ ใบจัดของ + ใบส่งสินค้า + ใบกำกับภาษี + ใบแจ้งหนี้  ของรอบ 1
   │                                        (ยอดตามของที่ส่งจริงในรอบนั้น)
   │  ของค้างส่ง
   └──────▶ รอบ 2 (เมื่อของเข้า)   ──▶ ชุดเอกสารใบใหม่ของรอบ 2
```

- **★ ยอดบิลไม่เคยขยับ** ตั้งแต่ต้นจนจบ — นี่คือโจทย์ตั้งต้น (ถ้าแยกบิล ยอดจะตกจนไม่ถึงขั้นส่วนลดท้ายบิล)
  · **ผลรวมทุกรอบ = ยอดบิลเป๊ะ** ทั้งยอดรวม ก่อนภาษี และภาษี (รอบสุดท้ายรับเศษที่เหลือ)
- **ออกใบกำกับภาษี/ใบแจ้งหนี้แยกตามรอบ** — จุดที่ภาระภาษีเกิดคือตอนส่งของ ไม่ใช่ตอนรับออร์เดอร์
  (เปลี่ยนจากแผนเดิมที่จะออกใบเดียว หลังดูระบบ SalesTools ที่แอดมินศูนย์โชว์ให้)
- กด "จัดส่งสำเร็จ" ขณะยังมีของค้าง = **ปิดรอบนี้แล้วเปิดรอบถัดไป ไม่ใช่ปิดบิล** (กลับไป `accepted`)
  — แอดมินกดปุ่มเดิมปุ่มเดียว ระบบตัดสินเองจากของที่ยังไม่ได้ส่ง
- ของรอบที่ปิดแล้ว **ห้ามคืนเข้าคลัง** (ถึงมือลูกค้าไปแล้ว)
- **`saleDeliveryPlan()` = แหล่งความจริงเดียว** ของ "สั่งเท่าไร ส่งไปแล้วเท่าไร ค้างเท่าไร"
- ไฟสถานะของบนหน้ารายการบิล (เขียว/ส้ม/แดง) คำนวณให้ทุกใบในคำขอเดียว (`getSalesOrderStockFlags`)
  **★ ไฟตอบว่า "ใบนี้หยิบของได้จริงไหม"** ซึ่งขึ้นกับบิลอื่นที่จองของชิ้นเดียวกันไว้ —
  เทสต์ต้องเทียบกับ `saleDeliveryPlan` ของใบเดียวกัน **ห้ามคาดสีเป็นค่าตายตัว**

### 2.1 สองชั้นต้องผ่านทั้งคู่ อย่ายุบรวม

```
ชั้น A  บริษัท "มอบ" ชุดให้ตัวแทนรายไหน     package_tenants (38_package_distribution.gs)
        ★ ไม่ระบุตัวแทน = ไม่มีใครได้ (ไม่ใช่ "ทุกคน")
        ★ ตัวแทนแก้ไม่ได้เลย แม้บทบาทจะมีสิทธิ์ edit
        ★ ตัวแทนว่าง (ขายตรง) เทียบกับ HOUSE — ต้องจ่ายชุดให้ HOUSE ด้วย ไม่ได้ฟรีอัตโนมัติ
   │
   ▼
ชั้น B  ภายในตัวแทนนั้น ร้านแบบไหน "ได้ใช้"   price_list_rules (36_price_rules.gs)
        เงื่อนไขอ้างคุณลักษณะลูกค้า (PLR_FIELDS) รวม attr:<key> และ member_of_list
        ★ กฎที่ไม่มีเงื่อนไข = ไม่ผ่าน (ไม่ใช่ครอบคลุมทุกคน)
        ★ ลำดับตัดสิน: priority สูงสุด → valid_from ใหม่สุด → record_id สูงสุด (ต้องครบทุกชั้น
          ไม่งั้นลูกค้าคนเดียวได้คนละราคาในสองคำขอติดกัน)
```

เขียนกฎ `tenant_id = X` แทนชั้น A **ไม่ได้** เพราะตอบคำถาม "ตัวแทนนี้มีชุดอะไรบ้าง" ไม่ได้
โดยไม่ไล่ลูกค้าทีละราย

ใช้โครงเดียวกันทั้ง **ชุดราคา · โปรโมชั่น · ชุดแถม** (`package_type` / `target_type`)

### 2.2 ลำดับการคิดเงิน (`priceCart` ใน `18_pricing_engine.gs`)

```
ราคาตามขั้น (หีบ/ลังรวมทั้ง line_id)  →  หักโปร  →  หักส่วนลดท้ายบิล  →  ถอด VAT
```

- **ขั้นราคานับรวมทั้งตระกูล** — สินค้าที่ใช้ `line_id` เดียวกัน (กลิ่นต่างกันของสินค้าเดียวกัน)
  นับหีบรวมกัน แล้วทุกหีบได้ราคาของขั้นที่ยอดรวมถึง
- **★ เกณฑ์ขั้นส่วนลดท้ายบิลวัดจากยอดก่อนหักโปร แต่ฐานที่เอาไปคูณ % หักโปรออกก่อน**
  — วัดหลังหักโปรจะทำให้โปรกลายเป็นตัวทำให้หลุดขั้น แล้วลูกค้าได้ส่วนลดรวม*น้อยลง*กว่าไม่มีโปร
- **`computePromoDiscount()` เป็นแกนเดียวของทั้งสองเส้นทาง** (เส้นทางเดิมและเส้นทางชุดราคา)
- ร้านที่มีชุดราคาเปิดอยู่ = ชุดนั้นเป็น**แหล่งราคาเดียว** สินค้าที่ไม่อยู่ในชุดขายให้ร้านนั้นไม่ได้
  · กลุ่มที่ไม่มีชุด active ตกไปใช้เครื่องยนต์เดิม (`applyPromotions`) โดยไม่ถูกแตะ
- แพ็ค (PK) ขายได้**เฉพาะ Cash Van และเฉพาะเงินสด** — บังคับที่เซิร์ฟเวอร์ (`PACK_VAN_ONLY`/`PACK_CASH_ONLY`)
- `sales_orders.discount` เก็บส่วนลด**รวมทุกชั้น** ให้ `subtotal − discount = total` เสมอ

### 2.3 ของแถม (`39_free_goods.gs`)

- **★ `tier_group` = กลไกเดียวกันหลายขั้น → ได้ขั้นสูงสุดที่ถึง "ขั้นเดียว"**
  ใบอนุมัติเขียน "ซื้อ 12 ลัง FOC 1 ลัง · ซื้อ 6 ลัง FOC 6 แพ็ค · ซื้อ 1 ลัง FOC 1 แพ็ค" = กลไกเดียวสามขั้น
  ถ้าปล่อยให้ทุกขั้นทำงาน ซื้อ 12 ลังจะได้ทั้งสามอย่าง = **แจกของฟรีเกินที่อนุมัติโดยไม่มีใครเห็น**
  · ขั้นที่ชนะคูณรอบได้ (24 ลัง → 2 ลัง) · **ขั้นสูงกว่าชนะแม้ให้น้อยกว่า** (7 ลัง → 6 แพ็ค ไม่ใช่ 7 แพ็ค)
- **หน่วยของแถมแยกจากหน่วยเงื่อนไข** ("ซื้อเป็นลัง แถมเป็นแพ็ค" เป็นเรื่องปกติ)
  · **ตัดสต็อกด้วยหน่วยฐานเสมอ** — ใช้ `qty` ตรงๆ = ตัดสต็อกน้อยไปเป็นสิบเป็นร้อยเท่า
- ของแถม **ไม่กระทบยอดเงิน** ไม่เข้าฐานส่วนลดใดๆ · เขียนเป็นบรรทัดบิล `is_free = 1` ราคา 0
- แยกจากชุดราคาโดยตั้งใจ: ช่วงเวลาไม่ตรงกัน (FOC 1–31 ก.ค. ในงวดราคา ก.ค.–ก.ย.)
  และของแถมถูกยกเลิก/ต่ออายุระหว่างงวดเป็นปกติ

ลูกค้า    customers.tax_type — exempt/zero = ทั้งใบไม่คิด VAT   (ยังไม่มีใครอ่าน — ดูข้อ 3.4)
   ▼
สินค้า    products.tax_status — ว่าง/vat = คิด · exempt/zero = ยกเว้น
          ★ คนละคอลัมน์กับ vat_type เดิมโดยตั้งใจ (vat_type ค่า default = 'none' ซึ่งแปลว่า
            "ยังไม่ได้ตั้ง" ไม่ใช่ "ไม่มีภาษี" เอามาใช้ตรงๆ = สินค้าทุกตัวกลายเป็นยกเว้นภาษีทันที)
```

### 3.2 กฎที่ห้ามแตะ

- **ราคาขายทุกช่องเป็นราคารวม VAT แล้ว** (ใบรายการขายของบริษัทพิมพ์ราคารวมภาษีมาแต่ไหนแต่ไร)
- **ถอดภาษีด้วย `splitVat(gross, rate?)` ที่เดียว** — การันตีว่า `exVat + vat === gross` เป๊ะทุกยอด
  **ห้ามเขียน `/1.07` เองที่อื่น** (ปัดเศษคนละที่ = ตัวเลขบนกระดาษกับในบัญชีต่างกันทีละสตางค์ แล้วงบไม่ลงตัว)
- **บิลเก็บภาพนิ่งภาษีครบตั้งแต่ตอนบันทึก** (`apply_vat` · `vat_type` · `vat_rate` · `vat_amount`
  · `subtotal_ex_vat` · `exempt_amount`) **ห้ามคำนวณใหม่ตอนเปิดดู** — วันที่รัฐเปลี่ยนอัตรา
  ใบเก่าทั้งหมดจะขยับตามและงบที่ปิดไปแล้วจะเคลื่อน (มีเทสต์ยืนยัน)
- **บิลใบเดียวมีของสองแบบปนกันได้** → `saleVatBreakdown()` · **ส่วนลดท้ายบิลต้องเฉลี่ยตามสัดส่วน
  มูลค่าของสองกลุ่ม** (ลดทั้งก้อนจากฝั่งคิดภาษี = คิดภาษีน้อยไป · ลดจากฝั่งยกเว้น = คิดภาษีเกิน)
- **`vatFlagOn()` เป็นตัวแปลง boolean ของ VAT โดยเฉพาะ** ห้ามใช้ `isNotOff`/`isFlagOn` แทน
  (หน้าตาเหมือนกันแต่ค่าว่างคนละความหมาย)
- **ไม่คิด VAT อย่าพิมพ์บรรทัด "ภาษีมูลค่าเพิ่ม 0.00"** — อ่านแล้วเหมือนคิดแล้วได้ศูนย์ ซึ่งคนละความหมาย
- ใบกำกับภาษีต้องแสดง "มูลค่าสินค้า" กับ "ภาษีมูลค่าเพิ่ม 7%" **แยกบรรทัด** (กฎหมายไทยบังคับ)

### 3.3 ยังไม่ก่อสร้าง
`customers.tax_type` ยังไม่มีใครอ่าน · ของแถมยังไม่ถูกคิดภาษี (ตามหลักสรรพากรมีภาระภาษีอยู่) ·
ยังไม่มีรายงานภาษีขาย/ซื้อแยกใบสำหรับยื่น ภ.พ.30 · ยังไม่มีปุ่มติ๊ก VAT รายใบ

## เส้นที่ 4 — ซื้อ → รับของ → หนี้ → จ่าย

```

- **สายอนุมัติเป็นข้อมูล ไม่ใช่โค้ด**: `approval_flows` (doc_type × ช่วงวงเงิน) + `approval_flow_steps`

  · ไม่มีสายเข้าเงื่อนไข = อนุมัติอัตโนมัติ (บันทึกไว้ในประวัติว่าระบบอนุมัติให้)
  · ปฏิเสธคนเดียว = ตีกลับทั้งใบ · ส่งใหม่ล้างประวัติเดิมเพื่อให้การนับเริ่มใหม่
  · `super_admin` อนุมัติแทนได้เสมอ (กันงานค้างเมื่อผู้อนุมัติไม่อยู่)
- **แก้ได้เมื่อไหร่**: PR แก้ได้เฉพาะ draft/rejected · PO แก้ได้เฉพาะ draft (ส่งผู้ขายแล้วต้องยกเลิกแล้วเปิดใหม่)
  · ยกเลิก PO ที่รับของแล้วไม่ได้ · ยกเลิก PO ที่ release จาก PR แล้วจะคืนยอดค้างให้ PR เอง
- **หน่วยสั่งซื้อ vs หน่วยฐาน**: `po_items.unit_factor` = จำนวนหน่วยฐานต่อ 1 หน่วยสั่งซื้อ
  · สต็อก/ต้นทุนทุกอย่างเก็บเป็น**หน่วยฐาน** · ต้นทุนเฉลี่ยถ่วงน้ำหนักคิดใหม่ทุกครั้งที่รับของ (`_applyStockIn`)
- ใช้ได้ทั้งบริษัทและตัวแทน แยกด้วย `tenant_id` ผ่าน `_scoped()` (ดูแผ่น 03 ข้อ 2)

  และ `createApBillFromGr` ปฏิเสธใบรับของที่มี `tenant_id` — ตัวแทนเป็นคนละนิติบุคคล

## เส้นที่ 7 — กันกดซ้ำ / กันบันทึกซ้ำ (สามชั้น)

อาการจริง: ผู้ใช้ไม่รู้ว่ากดไปแล้วหรือยัง โปรแกรมทำงานหรือยัง เลยกดซ้ำ → **ออร์เดอร์เข้าระบบสองใบ**

```
ชั้น 1  ปุ่มบอกว่ากดติดแล้ว     .btn:active ยุบลงทันทีที่นิ้วแตะ (ไม่รอ network)
        + .is-busy ระหว่างรอ   ซ่อนข้อความ ขึ้นวงหมุน ปิดปุ่ม
ชั้น 2  บล็อกที่จุดคอขวดเดียว   callApi() (แอดมิน) / api() (มือถือ)
        MUTATING_ACTIONS ที่ยังค้างอยู่ ยิงซ้ำไม่ได้ (ตอบ busy:true ก่อนถึง network)
ชั้น 3  กันจริงที่เซิร์ฟเวอร์     35_idempotency.gs — กันกรณีเน็ตหลุดหลังบันทึกสำเร็จแล้ว
        หน้าเว็บแนบ requestId · id เดิมเข้ามาอีก = คืนผลของครั้งแรก + duplicate:true
        เก็บผล 6 ชม. · ★ ผลที่ล้มเหลวไม่ถูกจำ (เพื่อให้แก้แล้วกดใหม่ได้จริง)
        ★ คีย์ผูกกับผู้ใช้+action ด้วย — สอง user ใช้ id ชนกันไม่ถือว่าซ้ำ
```

- **★ `requestId` ต้องสร้างตอน "ประกอบข้อมูลที่จะส่ง" ไม่ใช่ตอนยิงแต่ละครั้ง** ไม่งั้นการลองใหม่
  ได้ id ใหม่และกันอะไรไม่ได้เลย · แอปมือถือเก็บ `requestId` ไปกับบิลใน**คิวออฟไลน์**ด้วย
- **ลิสต์ชื่อ action อยู่สามที่** (`MUTATING_ACTIONS`/`IDEMPOTENT_ACTIONS` ฝั่งหน้าเว็บ กับ
  `IDEMPOTENT_ACTIONS` ฝั่ง backend) **ต้องเป็นชื่อที่มีจริงใน router** — พิมพ์ผิดแล้วเงียบ
  ไม่มีใครฟ้อง (เคยพลาด: ใส่ `createPurchaseOrder` ทั้งที่ชื่อจริงคือ `savePurchaseOrder`)
- เอกสารทุกใบเขียนผ่าน **`_withDocLock()`** — ยิงรัวๆ จะชนล็อก ("ระบบกำลังบันทึกเอกสารอยู่")
  สคริปต์ทดสอบต้องรอแล้วลองใหม่เอง ไม่ใช่ถือว่าระบบพัง
