# แผ่น 02 — ผังพื้น

โค้ดจัดเป็นชั้นอะไร · ของใหม่ควรไปวางที่ไหน

## 1. Backend — ชั้นล่างขึ้นชั้นบน

Apps Script **ไม่มี `import`** ทุกไฟล์อยู่ใน scope เดียวกันหมด เลขนำหน้าไฟล์คือ
**ลำดับที่โหลด** เท่านั้น (เลขน้อยอ่านก่อน) ไม่ได้บังคับการเรียก — แต่เราใช้เลขเป็นชั้น
เพื่อให้คนอ่านรู้ว่าอะไรพึ่งอะไร **ของที่คนอื่นเรียกเยอะต้องเลขน้อย**

```
ชั้น 0  โครงพื้น          00 setup_sheets · 01 config · 02 helpers · 03 cache
        └─ 02_helpers.gs คือ "ชั้นเข้าถึงข้อมูล" ทุกการอ่าน/เขียนชีตผ่านที่นี่
ชั้น 1  ทางเข้า + ตัวตน    04 auth(doPost) · 05 router · 14 permissions · 26 roles
        │                  27 line_auth · 29 admin_signup · 30 admin_line_login · 16 admin_users
        └─ 35 idempotency (กันบันทึกซ้ำ) · 32 admin_bootstrap (เปิดแอปคำขอเดียว)
ชั้น 2  ข้อมูลแม่          10 master_data · 33 customers · 28 units · 44 product_categories
                           40 customer_lists · 37 customer_bulk · 47 address_refs · 25 company
                           13 tenants (สร้าง/ดูแลไฟล์ของตัวแทน) · 24 drive_layout · 12 docnum
ชั้น 3  ราคาและส่วนลด      17 pricing(ชุดราคา) · 18 pricing_engine(priceCart) · 11 promotions
                           36 price_rules(ชั้น B) · 38 package_distribution(ชั้น A) · 39 free_goods
ชั้น 4  ขาย                07 sales(มือถือ) · 19 sales_admin · 34 sales_status · 48 delivery_rounds
                           08 stock(สต็อกรถ) · 09 visits · 31 sales_rollup · 41 sales_reports
ชั้น 5  ซื้อและคลัง         20 purchasing_master · 21 purchase_requisition · 22 purchase_order
ชั้น 6  บัญชี              23 accounting(GL/AP/AR/งบ) · 49 credit_notes(ใบลดหนี้/เพิ่มหนี้)
ชั้น 7  รอบข้าง            42 help_center · 43 external_sales_import · 45 unit_rescale
                           46 customer_requests · 15 import_export_express · 99 dev_tools
```

**กฎการวางของใหม่**: เรียกได้แต่ชั้นเดียวกันหรือชั้นล่างกว่า · ถ้าชั้นล่างต้องเรียกชั้นบน
แปลว่าวางผิดชั้น (ตัวอย่างที่ถูก: `34_sales_status` เรียก `48_delivery_rounds` ไม่ได้…
แต่มันเรียก เพราะรอบจัดส่งเกิดทีหลัง — **หนี้ทางโครงสร้างที่รู้ตัว** เลขไฟล์ควรเป็น 33.5)

### ชั้นเข้าถึงข้อมูล (`02_helpers.gs`) — ด่านเดียวของการอ่าน/เขียนชีต

| ฟังก์ชัน | ทำอะไร |
|---|---|
| `centralObjects(sheet)` | อ่านชีตกลางทั้งแผ่นเป็น array ของ object |
| `centralAppend` / `centralAppendMany` / `centralUpdate` / `deleteRowsWhere` | เขียน · **ล้างแคชให้อัตโนมัติ** |
| `centralInvalidate(sheet)` | **เขียนชีตแบบดิบต้องเรียกเอง** ไม่งั้นแคชค้างของเก่า |
| `tenantRowById` / `tenantRowsWhere` | อ่านไฟล์ตัวแทนแบบ **อ่านคอลัมน์คีย์ก่อน แล้วอ่านเฉพาะแถวที่ตรง** (ถูกกว่าอ่านทั้งแผ่น) |
| `updateColumnsWhere` | **เขียนหลายแถวต้องใช้ตัวนี้** เขียนครั้งเดียวต่อ "คอลัมน์" ไม่ใช่ต่อแถว |
| `isFlagOn` / `isFlagOff` / `isNotOff` | แปลง boolean ของ Sheets (ค่าว่าง/`'TRUE'`/`true` ปนกัน) |

**แคชสองชั้น**: `_objMemo` ต่อคำขอ + `CacheService` ข้ามคำขอ TTL 5 นาที
สำหรับตารางแม่ที่เปลี่ยนน้อย (`SHEET_CACHE_TABLES`)
· **ห้ามใส่ตารางเอกสาร/ตัวนับเลขที่/`liff_users`/`admin_users` เข้าลิสต์แคช**

## 2. ต้นทุนจริงของ Apps Script — ตัวกำหนดรูปร่างของทุกอย่าง

วัดบน UAT ไม่ใช่เดา:

| | เวลา |
|---|---|
| **ค่าคงที่ต่อ 1 คำขอ** (action ที่ไม่มีจริง แค่ routing) | **~1.6–2.1 วินาที** |
| เปิด Spreadsheet + อ่าน 1 ชีต | +~1.5–2.2 วินาที |
| อ่านชีตเพิ่มอีกแผ่นในไฟล์ที่เปิดแล้ว | +~0.45 วินาที |
| 4 คำขอเรียงกัน | 11.6 วินาที |
| **4 คำขอขนานกัน (`Promise.all`)** | **2.1 วินาที — เท่าคำขอเดียว** |
| payload 1.76 MB | +0.3 วินาที (**ขนาดข้อมูลไม่ใช่ตัวปัญหา**) |
| เพดานต่อ execution | 6 นาที |

**ผลที่ตามมาเป็นกฎออกแบบ 4 ข้อ**
1. **เปิดแอปยิงคำขอเดียว** — `getAdminBootstrap` คืนสิทธิ์ + บริษัท + ตัวแทน + แดชบอร์ด
   **ห้ามเพิ่มคำขอตอนเปิดแอป** ให้ยัดข้อมูลเข้า bootstrap
2. **หลังจากนั้นยิงขนานกันให้หมด** — การรวบหลายคำขอเป็น action เดียว *ไม่ช่วยอะไร*
   สิ่งที่ต้องไล่จับคือ **`await` เรียงกันเป็นทอดๆ** ในฟังก์ชันเดียว
3. **วาดจากของที่จำไว้ก่อนเสมอ** แล้วทับเมื่อของสดมา (ดูข้อ 3 ข้างล่าง)
4. **อย่าล้างของเก่าทิ้งแล้วนั่งรอ** — คำขอที่ไม่ทำอะไรเลยยังใช้ 1.5–2.9 วินาที

## 3. หน้าเว็บแอดมิน — 44 หน้าในไฟล์เดียว

`frontend-admin/index.html` ~9,400 บรรทัด · ไม่มี build step ไม่มี framework
(เลือกแบบนี้เพราะ deploy คือการวางไฟล์ และ debug คือการเปิด view-source)

ไฟล์ที่โหลดแยก: `config.js` (ไม่แคช) · `doc-print.js` + `pricelist-parser.js` +
`dragboard.js` (โหลดแบบ lazy ตอนจะใช้ครั้งแรก)

### ตัวกลางที่ทำให้หน้าใหม่ได้ของฟรี

**★ หน้าใหม่ไม่ต้องแก้ renderer เลย** ตัวกลางเหล่านี้ทำงานกับ DOM ที่วาดเสร็จแล้ว:

| ตัวกลาง | ให้อะไรฟรี |
|---|---|
| `initViewFrames()` | ห่อเนื้อหน้าใน `.view-body` — กรอบ/แถบเตือน/ตัวกรองตรึงอยู่ เลื่อนแค่ข้อมูล |
| `initTableSort()` | กดหัวคอลัมน์เพื่อเรียง · จำไว้ต่อตาราง · เรียงซ้ำหลัง renderer วาดใหม่ |
| `initTableSearch()` | แทรกแถวค้นหาใน `<thead>` (จึงถูกตรึงไปกับหัวตาราง) |
| `initTableFooters()` | ท้ายตารางบอกจำนวนรายการ · "แสดง X จาก Y" ตอนกรอง |
| `initMoneyAlign()` | ช่องที่ขึ้นต้นด้วย ฿ ชิดขวาเอง |
| `tblLoading(body, cols)` | ขึ้นสถานะโหลดโดย **ไม่ลบของเดิมทิ้ง** |
| `plModal()` / `plModalActions()` / `plBusy()` | โมดัล หัวเรื่องและปุ่มอยู่กับที่ เนื้อเลื่อน · ปุ่มขึ้นวงหมุนและปิดตัวเองระหว่างรอ |
| `callApi()` | จุดคอขวดเดียว — แนบ token/tenantId · กันกดซ้ำ · ป้าย "กำลังอัปเดต…" |
| `DocPrint.doc/table/xlsx` | เครื่องพิมพ์เอกสารกลาง (แบ่งหน้าด้วยการวัดความสูงจริง) |

ทั้งหมดนี้มาจากบทเรียนเดียว: *"กติกาในเอกสารไม่ช่วยถ้าไม่มีกลไกบังคับ"* — กฎ "วาดจาก snapshot ก่อน"
เขียนไว้ตั้งแต่ต้นแต่ใช้แค่หน้าแรก พอเพิ่มหน้าใหม่อีก 20 กว่าหน้าไม่มีใครขยายไปให้
จึงทำเป็นฟังก์ชันกลางให้หน้าใหม่ได้เอง

### ชั้นจำข้อมูล (ทำให้เปิดแอปเห็นของทันที ~60–74 ms)

| ชั้น | คีย์ | เก็บอะไร |
|---|---|---|
| `snapLoad`/`snapSave` | `topshop_<env>_snapshot` | ผล bootstrap ล่าสุด → เปิดแอปเห็นหน้าแรกทันที |
| `listSnapLoad`/`listSnapSave`/`listSnapDrop` | `topshop_<env>_lists` | รายการต่อหน้า (ลูกค้า/สินค้า/บิล/ชุดราคา) อายุ 24 ชม. |
| `SOD_PRE` + `sodPrefetch` | ในหน่วยความจำ | เอาเมาส์ชี้แถวบิล → ดึงรายละเอียดล่วงหน้า |

**★ ก้อนเกิน 500 KB ไม่เก็บ** และต้องลบของเก่าของคีย์นั้นด้วย ไม่งั้นค้างถาวร
**★ รายการที่ย่อฟิลด์แล้วห้ามหลุดเข้าฟอร์มแก้ไข** — กดบันทึกจะลบฟิลด์ที่ไม่ได้เก็บทิ้งเงียบๆ
(`custCachePartial` กั้นไว้ที่ `openCustomerModal`) · **ย่อรายการอื่นเพิ่มต้องกั้นแบบเดียวกันเสมอ**

### เมนู — ชุดเดียวใช้ทั้งสองฝั่ง

`NAV_GROUPS` ชุดเดียว เลขเดียวกันทุกคน (เดิมแยกเป็น `owner`/`tenant` แล้วเลขไม่ตรงกัน
คุยกันทีต้องถามก่อนว่าใครเห็นเลขอะไร) · ต่างกันแค่เห็น/ไม่เห็นและกดได้/กดไม่ได้ ตัดสินที่ **`navState(it)`**:

- `hidden` — ไม่ใช่งานของฝั่งนี้ (`scope`) และไม่ได้สั่งให้โชว์เทา
- `locked` — เห็นแต่กดไม่ได้ + เหตุผลใน tooltip (บริษัทคุมไว้ · ยังไม่ได้รับสิทธิ์ · ยังไม่ได้ทำ)
- `ok` — ใช้งานได้

กลุ่ม: 1 งานขาย · 2 งานซื้อ · 3 ข้อมูลสินค้า · 4 คลังสินค้า · 5 บัญชี · **6 สำรองไว้** ·
7 ผู้ใช้งานและสิทธิ์ · 8 เครือข่ายตัวแทน · 9 ตั้งค่าระบบ
(รายการเมนูทั้ง 39 รายการอยู่ใน [แผ่น 06 หมวด H](06-schedules.generated.md))

**เพิ่มเมนูใหม่ต้องใส่ `scope` ทุกครั้ง** (ไม่ใส่ = `both`) และโมดูลต้องอยู่ใน
`OWNER_MODULES`/`TENANT_MODULES` ของฝั่งนั้น ไม่งั้นเห็นแต่กดไม่ได้ตลอดไป

## 4. แอปมือถือ (LIFF) — 1,342 บรรทัด

หน้าเดียวจบ ธีมเดียวกับแอดมิน · ยืนยันตัวตนด้วย LINE ID token ทุกคำขอ ·
มี **คิวออฟไลน์** สำหรับบิลที่ยิงไม่สำเร็จ (เก็บ `requestId` ไปด้วย จึงส่งซ้ำได้โดยไม่เกิดบิลที่สอง)
· ปุ่มที่มีไอคอนต้องเขียน label ด้วย `innerHTML` ไม่ใช่ `textContent` ไม่งั้นไอคอนหายตอนเปลี่ยนสถานะ

## 5. ยังไม่ก่อสร้าง

- **`index.html` 9,400 บรรทัดเป็นไฟล์เดียว** — เป็นคอขวดตอนทำงานสองคน (กุญแจดอกเดียว)
  แต่ยังไม่แยกเพราะการแยกต้องมี build step ซึ่งแลกความง่ายของ deploy ไป
- **เลขไฟล์ `48_delivery_rounds` อยู่สูงกว่า `34_sales_status` ที่เรียกมัน** — หนี้ทางโครงสร้างที่รู้ตัว
- หน้าจอที่เมนูบอกว่า "เร็วๆ นี้" ยังเป็นโครงเปล่า (ดูแผ่น 06 หมวด H)
- **ใบลดหนี้/ใบเพิ่มหนี้ยังไม่มีหน้ารายการของตัวเอง** (เมนู 1.1.2 ยัง `ready:false`)
  ตอนนี้ออกได้จากหน้าลูกหนี้และแท็บการจัดส่งเท่านั้น — backend พร้อมแล้ว (`listArCreditNotes`/`listArDebitNotes`)
