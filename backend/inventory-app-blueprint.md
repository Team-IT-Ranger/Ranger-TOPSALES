เอกสารนี้ถอดแบบจากแอป **Hippo Village** (ระบบจัดการสินค้าคงคลังและการขาย กาแฟรักษ์นคร)

## 1. ภาพรวมสถาปัตยกรรม

### 1.1 แยกหน้าบ้าน–หลังบ้านออกจากกันเด็ดขาด

สองโปรเจกต์แยกกันคนละ deployment:

```
frontend/   เสิร์ฟ HTML ทั้งหมด ไม่แตะฐานข้อมูลเลย
backend/    เป็น API ล้วน ไม่เสิร์ฟ HTML แม้แต่บรรทัดเดียว
```

**ทำไมต้องเข้มขนาดนี้:** ตอนเริ่มโปรเจกต์มักมีโค้ดต้นแบบที่หลังบ้านเสิร์ฟหน้าเว็บอยู่ ถ้าปล่อยไว้ "ชั่วคราว"
สุดท้ายจะมีสองที่ที่เสิร์ฟ UI แล้วแก้ที่เดียวไม่ครบ — **แยกตั้งแต่วันแรก ถูกกว่าแยกทีหลังเสมอ**

### 1.2 ทุกคำขอเดินทางเดียว

```
ปุ่มบนหน้าจอ
  → callApi(action, payload, onSuccess)        // จุดคอขวดเดียวของฝั่ง client
    → handleAction(action, userId, payload)     // ห่อ log + จับ exception + จับเวลา
      → _handleActionCore()                     // ตรวจว่าเป็นผู้ใช้ที่อนุมัติแล้ว + lookup ACTION_MAP
        → ฟังก์ชันปลายทาง(user, payload)        // ตรวจสิทธิ์โมดูลของตัวเอง แล้วทำงาน
      ← { success: bool, message?, ...data }
```

**กติกาที่ทำให้ระบบอยู่รอด:**

| กติกา | เหตุผล |
|---|---|
| ทุกฟังก์ชันรับ `(user, payload)` เหมือนกันหมด | router ตัวเดียวเรียกได้ทุกตัว ไม่ต้องมีเคสพิเศษ |
| คืน `{success:true, ...}` หรือ `{success:false, message}` เสมอ | หน้าบ้านเขียนตัวจัดการผลลัพธ์ตัวเดียวใช้ได้ทุกที่ |
| **ห้ามเชื่อ `branchId` ที่ส่งมาจาก payload** | ใช้ `user.branchId` เสมอ ไม่งั้นแก้ payload แล้วอ่านข้ามสาขาได้ |
| ทุก action ต้องลงทะเบียนใน `ACTION_MAP` | ไฟล์ที่ยังไม่ deploy จะได้ error สุภาพเฉพาะ action นั้น ไม่พังทั้งแอป |

`[GAS]` lookup ด้วย `globalThis[fnName]` ไม่ใช่ `eval()` และถ้าหาไม่เจอให้คืนข้อความบอกว่า
"ไฟล์นี้อาจยังไม่ได้ deploy เป็น New Version" — ประหยัดเวลาไล่บั๊กได้มาก

### 1.3 สิทธิ์แบบสองมิติ

ไม่ใช่ `isAdmin` ตัวเดียว แต่เป็น **โมดูล × (ดู | แก้ไข)**

```js
var MODULE_REGISTRY = [
  { code: 'stock',        label: 'สินค้าคงคลัง' },
  { code: 'goodsreceipt', label: 'ใบรับสินค้า' },
  ...
];
// roles           : role_code, role_label, is_system
// role_permissions: role_code × module_code → can_view, can_edit
```

**รูปแบบบังคับใช้ — ทุกฟังก์ชันตรวจสิทธิ์ของตัวเอง ไม่ฝากไว้ที่ router:**

```js
function createGoodsReceipt(user, payload) {
  const err = _requirePermission(user, 'goodsreceipt', 'edit'); if (err) return err;
  // ...
}
```
- `list*` / `get*` → ขอสิทธิ์ `view`
- `add*` / `update*` / `create*` / `cancel*` → ขอสิทธิ์ `edit`
- **`super_admin` ข้ามการตรวจทุกกรณีโดยไม่มีเงื่อนไข** — ตั้งใจให้เป็นแบบนี้ เพื่อกันเคสตั้งค่าตารางสิทธิ์ผิดจนไม่มีใครเข้าไปแก้ตารางสิทธิ์ได้อีกเลย
- ไม่มีสิทธิ์ในตาราง = **ไม่ให้ผ่าน** (secure by default) ไม่ใช่ปล่อยผ่านโดยปริยาย

ฝั่งหน้าจอซ่อนเมนูตาม `permissions` ที่แนบมากับ bootstrap — แต่ถือเป็นแค่ความสวยงาม
**การบังคับจริงอยู่ที่หลังบ้านเท่านั้น** หน้าจอซ่อนพลาดไม่เป็นไร หลังบ้านต้องไม่พลาด

> ⚠️ **กับดักแคช:** ข้อมูลระดับสาขาแคชได้ แต่ **สิทธิ์เป็นของ role ไม่ใช่ของสาขา**
> ต้องคำนวณสิทธิ์ใหม่ทุกครั้งหลังดึงแคช และห้ามให้สิทธิ์ไหลผ่านตัวแคชเด็ดขาด
> ไม่งั้นสองคนคนละ role ในสาขาเดียวกันจะได้สิทธิ์ของกันและกัน

## 2. ระบบข้อมูลสินค้า

### 2.1 รวมตารางสินค้าเป็นตารางเดียว แยกด้วย `item_kind`

เดิมแยก `raw_materials` กับ `products` เป็นคนละตาราง สุดท้ายรวมเป็น **`products` ตารางเดียว**:

```
products: record_id, company_id, item_kind, name, unit, item_code,
          origin, cost_per_kg, reorder_kg,                    ← ใช้เฉพาะ item_kind='raw'
          roast_level, package_size_g, price_retail,
          price_wholesale, reorder_bags, cost_per_unit,       ← ใช้เฉพาะ item_kind='finished'
          external_code, barcode, primary_img, vat_applicable, is_active
```

**ทำไมถึงรวม:**
- `record_id` เป็นลำดับเดียวทั้งระบบ **ไม่มีทางที่วัตถุดิบกับสินค้าสำเร็จรูปจะชนเลข id กัน**
  (ตอนแยกตาราง ทั้งสองฝั่งมี id 5 ได้พร้อมกัน แล้ว `stock_movements` ที่เก็บแค่ `item_id` ก็แยกไม่ออก)
- ฟังก์ชันที่ต้องวนสินค้าทุกชนิด (ค้นหา, รายงาน, สต็อก) เขียนครั้งเดียวจบ

**ราคาที่ต้องจ่าย และวิธีอยู่กับมัน:**
- ตารางกว้างและมีช่องว่างเยอะตามชนิด — **ตั้งใจให้เป็นแบบนี้ ไม่ใช่ความผิดพลาด**
- ⚠️ **ทุกครั้งที่อ่านตารางนี้ต้องกรอง `item_kind` ก่อนเสมอ**
  ```js
  companyRows('products', companyId).filter(p => p.item_kind === 'raw');
  ```
  ถ้าลืมกรอง จะได้ของสองชนิดปนกันแบบเงียบ ๆ (เคยหลุดไปสองที่: การนับของใกล้หมด และหน้าสต็อก)

วัสดุสิ้นเปลืองแยกตาราง `consumables` ต่างหาก เพราะไม่มีฟิลด์ร่วมกับอีกสองชนิดเลย

### 2.2 `item_code` — รหัสประจำตัวสินค้าที่ใช้ได้กับทุกชนิด

บทเรียน: เคยมีฟิลด์ที่ถูกใช้ซ้ำโดยฟีเจอร์ต่าง ๆ ในความหมายคนละอย่าง (ครั้งแรกเป็น FK ไปวัตถุดิบ
ต่อมาเป็นรหัสจากไฟล์นำเข้า) สุดท้ายต้อง **นิยามให้ชัดแล้วใช้ความหมายเดียวทั้งระบบ**

```
item_code = รหัสธุรกิจของสินค้าตัวนั้น (เหมือนเลขบัตรประชาชนของสินค้า)
            ใช้กับทุก item_kind — FG-0001, RM-0001, PM-0001
            ไม่ใช่ foreign key ไปหาอะไรทั้งสิ้น
```

**กติกาที่ตามมา — ใส่ให้ครบทุกที่:**
- นำเข้าไฟล์ → **จับคู่ด้วย `item_code` ก่อนเสมอ** แล้วค่อย fallback ไปจับคู่ด้วยชื่อ (ตัดช่องว่าง + ไม่สนตัวพิมพ์)
- dropdown เลือกสินค้า → แสดง `[FG-0001] ชื่อสินค้า`
- ช่องค้นหา → ค้นได้ทั้งชื่อและรหัส
- ตาราง/รายงาน/เอกสารพิมพ์ → มีคอลัมน์รหัสสินค้า

> ไม่ได้บังคับ unique ในระดับฐานข้อมูล — ถ้าโปรเจกต์ใหม่ทำได้ **ควรบังคับตั้งแต่แรก**

### 2.3 ตั้งชื่อ primary key ว่า `record_id` ไม่ใช่ `id`

```
record_id  = กุญแจหลักของแถวในตาราง (ภายในระบบ)
item_code  = รหัสธุรกิจ (คนอ่าน)
id         = ชื่อฟิลด์ใน JSON ที่ส่งให้หน้าบ้าน (สัญญา API ไม่เปลี่ยน)
```

แยกคำสามคำนี้ให้ขาด แล้วความสับสนจะหายไปทั้งก้อน

> ⚠️ **กับดักที่เคยพลาดจริง:** ตอนเปลี่ยนชื่อคอลัมน์ `id` → `record_id` ใช้ find-and-replace
> แล้วมันไปแก้ `payload.id` (ชื่อฟิลด์ที่หน้าบ้านส่งมา ซึ่งไม่เกี่ยวอะไรกับชื่อคอลัมน์) ด้วย
> → ฟังก์ชันแก้ไข/ลบทุกตัวพังหมด
> **บทเรียน: ก่อน rename ทุกครั้ง ให้ `grep 'payload\.[a-zA-Z_]+' แล้วไล่ดูทีละชื่อก่อน**

## 3. การจัดการข้อมูล

### 3.1 ชั้นเข้าถึงข้อมูลบาง ๆ ที่ต้องมี

ไม่ว่าฐานข้อมูลจะเป็นอะไร ให้มีชุดนี้เป็นทางผ่านเดียว:

| ฟังก์ชัน | หน้าที่ |
|---|---|
| `sheetToObjects(name)` | อ่านทั้งตารางเป็น array ของ object พร้อมแนบ `_row` (เลขแถวจริง) |
| `appendRowGAS(name, obj)` | เติมแถวใหม่ **โดยเรียงตาม header จริงของตาราง** |
| `appendRowsGAS(name, [obj])` | เติมหลายแถวรวดเดียว |
| `updateRowGAS(name, row, patch)` | แก้เฉพาะฟิลด์ที่ส่งมา |
| `nextId(name)` | ออกเลข record_id ถัดไป |
| `companyRows(name, companyId)` | อ่านเฉพาะแถวของบริษัทนั้น |

**จุดสำคัญสองข้อ:**

1. **เขียนแถวใหม่ต้องเรียงตาม header จริงที่อ่านมา ห้ามไล่ตำแหน่งคงที่**
   ```js
   const newRow = hdr.map(h => obj[h] !== undefined ? obj[h] : '');
   ```
   เพราะตารางเก่าที่ผ่านการเติมคอลัมน์มาทีหลัง จะมีคอลัมน์ใหม่ต่อท้าย ไม่ได้อยู่ตำแหน่งตามสคีมาใหม่
   → เขียนด้วย array ตำแหน่งตรง ๆ จะลงผิดคอลัมน์แบบเงียบสนิท (เคยเจอตอนย้ายคลังครั้งแรก)

2. **`_row` ที่แนบมาตอนอ่าน ใช้ update ได้ทันที** ไม่ต้องวนหาแถวใหม่ — เร็วขึ้นมากเมื่อข้อมูลเยอะ

### 3.2 การเพิ่มคอลัมน์ทีหลัง (schema migration)

ระบบที่ใช้งานจริงแล้วจะมีข้อมูลอยู่ การเพิ่มฟิลด์ใหม่ต้องไม่ทำให้ต้องแก้ตารางด้วยมือ

```js
// _ensureColumns(sheet, expectedHeaders)
// เทียบ header จริงกับที่คาดหวัง แล้ว "เติมคอลัมน์ที่ขาดต่อท้าย" โดยไม่แตะข้อมูลเดิม
// setupSheets() เรียกให้อัตโนมัติกับทุกตารางที่มีอยู่แล้วในทุกครั้งที่รัน
```

**ผลคือ:** เพิ่มฟิลด์ใหม่ = เพิ่มชื่อลงใน array ของสคีมาแล้วรัน `setupSheets()` ซ้ำ จบ
ไม่ต้องเขียนสคริปต์ migration แยก ไม่ต้องเข้าไปแก้ Sheet เอง

> สำหรับฐานข้อมูลจริง (Postgres) แนวคิดเดียวกันคือ `ADD COLUMN IF NOT EXISTS` ที่รันได้ซ้ำ ๆ โดยไม่พัง

### 3.3 แคชสองชั้น

```
ชั้นที่ 1  _sheetValuesCache   ในหน่วยความจำ อายุเท่ากับหนึ่ง execution
           → อ่านตารางเดิมซ้ำในคำขอเดียวกันไม่เสียเวลาอีก
ชั้นที่ 2  CacheService         ข้ามคำขอ (bootstrap 10 นาที / dashboard 2 นาที)
           → แยก key ตามสาขา: cachePut('bootstrap', branchId, data, TTL)
```

**กติกาการล้างแคช:**
- แก้ข้อมูลของสาขาเดียว → `cacheClearBranch(branchId)`
- แก้ข้อมูลระดับบริษัท (เช่นสร้างสินค้าใหม่ หรืออัปเดตต้นทุนมาตรฐาน) → `cacheClearAllBranches()`
- **อะไรที่เป็นของ role ห้ามเข้าแคชที่แยกตามสาขา** (ดูข้อ 1.3)

### 3.4 วันที่ — จุดที่พังเงียบที่สุดในระบบ

**ปัญหาจริงที่เจอ:** ค่า Date ที่ซ้อนอยู่ใน array ของ response ทำให้ฝั่ง client
deserialize ไม่ผ่าน — **หลังบ้านทำงานสำเร็จและ log ว่า OK แต่หน้าจอขึ้น error** ไล่หาสาเหตุยากมาก

แถม Google Sheets ยัง **แปลงสตริงที่หน้าตาเหมือนวันที่กลับเป็น Date object ตอนอ่าน** ได้เองด้วย
ขึ้นกับรูปแบบของเซลล์ ไม่เกี่ยวว่าตอนเขียนเราเขียนเป็นอะไร

**ทางแก้ที่ต้องทำให้เป็นระบบ:**

```js
safeDateStr(v)   // Date → 'yyyy-MM-dd HH:mm:ss', อย่างอื่น → String(v)
safeDateOnly(v)  // Date → 'yyyy-MM-dd'           (ใช้กับคอลัมน์ที่เป็นวันที่ล้วน)
```

- **ทุกฟิลด์เวลาที่ส่งกลับหน้าบ้านต้องผ่าน `safeDateStr()`**
- **การ sort ด้วยเวลาต้องเทียบ `safeDateStr(a.x)` กับ `safeDateStr(b.x)`**
  ไม่ใช่ `String(dateObject)` — เพราะจะได้ลำดับตามชื่อวันในสัปดาห์ ("Fri" < "Mon" < "Thu")
  ซึ่งเป็นบั๊กที่เงียบกว่าเดิมอีก (ไม่ error แค่เรียงผิด)

### 3.5 แยก "วันที่ทำรายการ" ออกจาก "เวลาที่บันทึก"

```
created_at        เวลาที่กดบันทึกจริง (audit)
transaction_date  วันที่ของรายการตามความจริงทางธุรกิจ (ย้อนหลังได้)
```

**รายงานทุกตัวต้องใช้ `transaction_date` เป็นหลัก แล้ว fallback ไป `created_at`**
ถ้าไม่แยกสองอย่างนี้ การบันทึกย้อนหลัง (ซึ่งเกิดขึ้นเสมอในงานจริง) จะทำให้รายงานผิดงวด

## 4. รูปแบบการแสดงผล

### 4.1 Design token — ห้าม hardcode สีในคอมโพเนนต์ใหม่

ประกาศเป็น CSS custom properties ชุดเดียวบน `:root` แล้วอ้างทุกที่:

```css
--brand / --brand-dk / --brand-md / --brand-lt      /* สีหลักไล่น้ำหนัก */
--success / --warn / --danger / --info (+ -lt)      /* สีความหมาย แยกจากสีแบรนด์ */
--ink / --ink-2..5                                  /* ระดับความเข้มของตัวอักษร */
--line / --line-2 / --bg / --bg-2 / --surface       /* เส้นและพื้น */
--r-xs..--r-xl / --r-pill                           /* รัศมีมุม */
--sh-xs..--sh-lg                                    /* เงาไล่ระดับ */
```

**สีความหมาย (เขียว/เหลือง/แดง) ต้องแยกจากสีแบรนด์** ไม่งั้นพอต้องบอกสถานะจะไปหยิบสีแบรนด์มาใช้
แล้วผู้ใช้อ่านไม่ออกว่าอันไหนคือ "ปกติ" อันไหนคือ "ต้องดู"

### 4.2 ตารางข้อมูล

**คลาสที่ใช้ซ้ำ:** `.data-table` `.cell-strong` `.cell-muted` `.cell-num` `.cell-date` `.mono` `.tag` `.empty-txt` `.loading-txt`

**กดหัวคอลัมน์เพื่อเรียง** — สามข้อที่ต้องทำให้ถูก:
1. เก็บข้อมูลที่โหลดมาไว้ในตัวแปร (`STOCK_GROUPS`) **เรียงใหม่ไม่ต้องยิง API ซ้ำ**
2. ตัวเลขเรียงแบบตัวเลข ข้อความไทยเรียงด้วย `localeCompare` — ไม่ใช่เรียงสตริงล้วน
   (`10` ต้องมาหลัง `9`, `FG-10` ต้องมาหลัง `FG-2`)
3. หัวคอลัมน์ที่กำลังเรียงอยู่ต้องมีลูกศรบอกทิศ

**แถวยอดรวมของกลุ่ม** — ใช้แถบสีเข้มคอนทราสต์ชัด ไม่ใช่สีอ่อนกลืนพื้น
และต้องซื่อสัตย์กับหน่วยที่ปนกัน (ถ้ากลุ่มมีทั้ง กก. และ ถุง ห้ามบวกรวมกันแล้วโชว์เลขเดียว)

### 4.3 เมนูหลายชั้น

โครง 3 ชั้น: **กลุ่ม → กลุ่มย่อย → คำสั่ง** + ส่วน Favorites / Recent (เก็บใน localStorage แยกตามผู้ใช้)

บทเรียนจากการทำเมนู hover ให้ใช้ได้จริง:
- **เมนูชั้นที่ 3 ควรออกไปเป็นแผงลอยด้านขวา** (แบบ Microsoft Dynamics 365) ไม่ใช่กางลงในแถบเดิม
  เพราะกางในแถบเดิมแล้วรายการล่างจะกระโดดหนีเคอร์เซอร์
- ต้องมี **หน่วงเวลาก่อนหุบ** (~0.9 วินาที และ ~1.5 วินาทีเมื่อมีแผงลอยเปิดอยู่) ไม่งั้นเลื่อนเมาส์ไปไม่ทัน
- ต้องมี **ตัวตรวจว่ากำลังเล็งไปทางแผงลอยอยู่หรือเปล่า** (เลื่อนทแยงมุมไปหาแผง ต้องไม่ถือว่าออกจากเมนู)
- ต้องมี **ช่วงนิ่ง** — ห้ามสลับเมนูระหว่างที่มือยังเคลื่อนอยู่

> ⚠️ **กับดักตัวจริง:** `mousemove` **bubble ขึ้นไปหา parent** ส่วน `mouseenter` **ไม่ bubble**
> → โค้ดที่ยกเลิก timer ของ "เมนูอื่น" ตอน mousemove จะไปฆ่า timer ของเมนูลูกตัวเองด้วย
> ต้องเช็คความสัมพันธ์ทั้งสองทาง: `if (b === keep || b.contains(keep) || keep.contains(b)) continue;`
> (เช็คแค่ `b.contains(keep)` = ปกป้องแต่บรรพบุรุษ ลูกยังโดนปิดอยู่ดี)
>
> และ `mouseenter` **ไม่ยิงย้อนหลัง**ให้เคอร์เซอร์ที่อยู่ในพื้นที่อยู่ก่อนแล้ว
> ตอนที่แผงด้านบนหุบหายไป หรือกล่องขยายใหญ่ขึ้นมาใต้เคอร์เซอร์ ต้องจัดการเคสนี้เอง

### 4.4 การเคลื่อนไหว

- ใช้ `max-height` ที่วัดค่าจริงด้วย JS แล้วค่อย transition — **`height:auto` และ `none` transition ไม่ได้**
- ครั้งแรกที่เปิดต้องตรึงเป็น `0px` แล้ว force reflow ก่อน ไม่งั้นค่าเริ่มต้นเป็น `none` แล้วจะกระโดด
- ให้ **ยืดเร็ว หุบช้า** (เช่น 0.55s / 0.80s) — เมนูหุบเร็วทำให้คนตกใจมากกว่าเมนูกางช้า

### 4.5 ป้องกันการกดซ้ำ

ทำที่ **จุดคอขวดเดียว** คือ `callApi()` ไม่ใช่ไล่ใส่ทีละปุ่ม:

```js
const MUTATING_ACTIONS = new Set(['createGoodsReceipt', 'setOpeningBalance', ...]);
// ระหว่างที่ action เดิมยังค้างอยู่ การเรียก action ชื่อเดียวกันซ้ำจะถูกบล็อกก่อนถึง network
// พร้อมปิดการใช้งานปุ่มที่เพิ่งกด (หาจาก document.activeElement) และปลดล็อกพร้อมกันทั้งสองทาง
```
**เวลาเพิ่ม action ใหม่ที่เขียนข้อมูล ให้ถือว่า "ลงทะเบียนใน router" กับ "ใส่ใน MUTATING_ACTIONS" เป็นขั้นตอนเดียวกัน**
ลืมใส่ไม่พัง แต่จะเสียการป้องกันไปเงียบ ๆ เฉพาะตัวนั้น

## 5. การคำนวณ

### 5.1 โมเดลบัญชีสต็อก

สองตารางทำงานคู่กัน:

```
branch_stock     ยอดคงเหลือปัจจุบัน (branch × warehouse × item)  — ตัวเลขเดียวต่อช่อง
stock_movements  บัญชีรายการเคลื่อนไหว เก็บเป็น "ผลต่าง" ทุกแถว   — append เท่านั้น
```

**กติกาเหล็ก: ทั้งสองต้องกระทบยอดกันได้เสมอ**
ทุกครั้งที่แตะ `branch_stock` ต้องเขียน `stock_movements` ด้วยเสมอ และกลับกัน

```js
moveStock(branchId, warehouseId, itemType, itemId, deltaQty,
          moveType, refId, unitCost, note, createdBy, transactionDate)
// = adjustBranchStock(...) + logStockMovement(...)  ทำคู่กันเสมอ

moveStockBatch(...)  // รุ่นเขียนทีเดียวหลายรายการ — ใช้กับการนำเข้าไฟล์/รับของหลายรายการ
                     // (เขียนทีละแถวในลูปทำให้การนำเข้าช้ามากจนใช้งานไม่ได้)
```

### 5.2 ประเภทการเคลื่อนไหว

```
goods_receipt     รับสินค้าเข้า (ทางเดียวที่เพิ่มสต็อกจากการรับของ)
opening_balance   ตั้งยอดยกมาตั้งต้น
internal_use / waste / sample / stock_out_other   จ่ายออกตามเหตุผล
transfer_out / transfer_in     โอนระหว่างสาขา
warehouse_move                 ย้ายคลังภายในสาขาเดียวกัน (เกิดเป็นคู่เสมอ)
count_adjustment               ปรับยอดจากการตรวจนับ
sale_out / sale_cancel         ขายออก / ยกเลิกใบขายคืนสต็อก
import_undo                    ถอนการนำเข้าจากแพลตฟอร์ม
```

> ⚠️ **`warehouse_move` ต้องไม่ถูกนับเป็นรับเข้า/จ่ายออกตอนดูภาพรวมทั้งสาขา**
> เพราะมันเกิดเป็นคู่ (ออกจากคลังหนึ่ง + เข้าอีกคลังหนึ่ง) หักล้างกันสุทธิเป็นศูนย์
> ถ้านับ จะโชว์ว่า "รับ +1 จ่าย -1" ทั้งที่ของยังอยู่ครบในสาขาเดิม
> แต่ถ้าเจาะดูรายคลัง มันคือรับเข้า/จ่ายออกจริงของคลังนั้น ต้องนับ

### 5.3 ยอดยกมาตั้งต้น — "ตั้งค่า" ไม่ใช่ "บวกเพิ่ม"

นี่คือส่วนที่คนทำระบบคลังพลาดกันบ่อยที่สุด

**วิธีที่ผิด:** บันทึกยอดตั้งต้นเป็นรายการรับเข้า (+120)
→ ถ้าภายหลังมีคนบันทึกรายการย้อนหลัง**ก่อน**วันตั้งยอด ยอด ณ วันตั้งยอดที่คำนวณจากบัญชีรายการจะขยับตาม
→ ตัวเลขที่ประกาศไว้เพี้ยน และไม่มีใครรู้ว่าเพี้ยนเมื่อไหร่

**วิธีที่ถูก:** เก็บเป็น **ค่าสัมบูรณ์ในตารางของตัวเอง**

```
opening_balances: branch_id, warehouse_id, item_type, item_id,
                  as_of_date, qty, unit_cost, note, created_by, created_at
  กุญแจ = (คลัง × สินค้า × งวด) — บันทึกซ้ำงวดเดิม = ทับแถวเดิม, งวดใหม่ = แถวใหม่
```

หลักการที่ตามมา:
1. ตัวเลขที่กรอก = **ยอดที่ต้องการให้เป็น** ระบบเขียนทับ `branch_stock` ตรง ๆ (`setBranchStockQty` ไม่ใช่ `adjustBranchStock`)
   → **โยนไฟล์เดิมซ้ำสองครั้งยอดไม่เบิ้ล**
2. **ไม่ออกเอกสารรับสินค้า** เพราะการประกาศยอดตั้งต้นไม่ใช่การรับของเข้าคลัง
3. บัญชีรายการยังต้องเขียนเป็นผลต่างเท่าที่ยอดขยับจริง (เพื่อให้กระทบยอดกับ `branch_stock` ได้)
   แต่ตัวเลขที่ประกาศอยู่ในตารางของตัวเอง **ไม่เพี้ยนตามอะไรทั้งนั้น**
4. **บังคับให้เป็นวันที่ 1 ของเดือนเท่านั้น** (หน้าจอใช้ช่องเลือกเดือน หลังบ้านตรวจซ้ำด้วย regex)
   ยอดยกมากลางเดือนทำให้แบ่งงวดไม่ตรงรอบบัญชี
5. เก็บ **ประวัติแบบเขียนอย่างเดียว** (`opening_balance_logs`) ทุกครั้งที่บันทึก พร้อมค่าก่อน/หลัง
   แก้ทับได้เสมอ แต่ต้องตามรอยได้ว่าใครแก้อะไรเมื่อไร

### 5.4 รายงานสรุปความเคลื่อนไหว — สองเส้นทางคำนวณ

```
ยอดยกมา (beg) → รับเข้า (in) → จ่ายออก (out) → ยอดคงเหลือ (end)
```

**เส้นทาง A — ไม่มีค่าประกาศ: คำนวณย้อนกลับจากปัจจุบัน**
```
end = ยอดคงเหลือปัจจุบัน − ผลรวมรายการที่เกิดหลังวันสิ้นงวด
beg = end − in + out
```

**เส้นทาง B — มีค่าประกาศยอดยกมา: คำนวณไปข้างหน้าจากค่าประกาศ**
```
beg = ค่าประกาศ + รายการระหว่างวันประกาศถึงต้นงวด
end = beg + in − out
รายการที่ลงวันที่ "ก่อน" วันประกาศ → อยู่นอกบัญชี ไม่นับเลย
แถวประเภท opening_balance → ไม่นับซ้ำ เพราะค่าประกาศแทนมันอยู่แล้ว
```

**เงื่อนไขเลือกเส้นทาง — จุดที่เคยพลาด:**
> ค่าประกาศมีผล **ตั้งแต่วันที่ประกาศเป็นต้นไปเท่านั้น**
> ถ้างวดที่ขอดู **เริ่มก่อน** วันตั้งยอด (รวมถึงงวดที่คร่อมวันตั้งยอด) → ต้องใช้เส้นทาง A
> ไม่งั้นย้อนดูเดือนสิงหาคมจะได้ตัวเลขของ 1 กันยายนมาเป็นยอดยกมา ซึ่งผิด

**กรณีหลายคลัง:** ถ้าดูรวมทุกคลังแล้วแต่ละคลังประกาศคนละวัน — **รวมกันไม่ได้อย่างมีความหมาย**
ให้ตีเป็น `mixed` แล้วถอยไปใช้เส้นทาง A พร้อมบอกผู้ใช้ว่าทำไม

**ต้องบอกผู้ใช้เสมอเมื่อตัวเลขมีที่มาพิเศษ:** แสดงแถบแจ้งว่ายอดยกมายึดค่าที่ประกาศ ณ วันไหน
มีกี่รายการที่ถูกตัดออกเพราะลงวันที่ก่อนวันตั้งยอด และเตือนว่ายอดคงเหลือหน้าสต็อกอาจไม่ตรงกับยอดสิ้นงวดในรายงาน
**อธิบายให้ชัดดีกว่าแอบกลบ**

### 5.5 ยอดจองและยอดพร้อมขาย

```
qty        ยอดคงเหลือจริงในคลัง
reserved   ยอดที่ถูกใบขายที่ยืนยันแล้วจองไว้ (stock_reservations, status='active')
available  qty − reserved   ← ฟอร์มใบขายต้องใช้ตัวนี้
```
ถ้าหน้าจอโชว์ `qty` แต่หลังบ้านตรวจ `available` ผู้ใช้จะเจอ "หน้าจอบอกว่ามีของ แต่กดบันทึกแล้วบอกไม่พอ"

**ประสิทธิภาพ:** รวมยอดจองเป็น map ครั้งเดียว แล้ว lookup — อย่าเรียกฟังก์ชันหายอดจองทีละรายการในลูป (กลายเป็น O(n²) ทันที)

### 5.6 การปัดเศษ

```js
function _stockQty(n){
  const v = Math.round((Number(n) || 0) * 1000) / 1000;   // ★ ปัดก่อนแสดงเสมอ
  return v.toLocaleString('th-TH', { maximumFractionDigits: 3 });
}
```
- **จำนวนสินค้าไม่ใช่เงิน** — ห้ามบังคับทศนิยม 2 ตำแหน่ง (54 ถุง ไม่ใช่ 54.00 ถุง)
- แต่วัตถุดิบชั่งเป็นกิโลกรัมจึงมีเศษได้ → **ต้องปัดก่อนแสดง** ไม่งั้นจะเจอ `12.299999999999999` โผล่บนจอ
- เงินใช้คนละตัว บังคับ 2 ตำแหน่งเสมอ (`_docMoney`)

### 6.2 แบ่งหน้าโดยวัดความสูงจริง ห้ามเดาจำนวนแถว

```js
// กล่องวัด: ใช้คลาส .docsheet ตัวเดียวกับกระดาษจริง ขนาด A4 เป๊ะ
// ต้องอยู่ในหน้าและมี layout จริง → ซ่อนด้วย position/visibility ห้ามใช้ display:none
//   (display:none วัดความสูงได้ 0 ทุกค่า)
m.className = 'docsheet doc-measure';
const overflow = () => m.scrollHeight > m.clientHeight + 1;
// ไล่เติมแถวจนเริ่มล้น แล้วถอยกลับหนึ่งแถว
```

**ทำไมเดาไม่ได้:** ขนาดตัวอักษรตั้งค่าได้ต่อบริษัท แต่ละหน้ามีคอลัมน์ไม่เท่ากัน
และชื่อสินค้ายาวไม่เท่ากันจนขึ้นบรรทัดใหม่ — เลขตายตัวจะผิดเสมอสักกรณี
น้อยไปเปลืองกระดาษ **มากไปข้อมูลถูกตัดหายเงียบ ๆ** (กระดาษเป็นกล่อง `overflow:hidden`)

**หน้าสุดท้ายต้องมีที่พอสำหรับยอดรวม + ช่องลงชื่อ** ถ้าไม่พอให้ผลักแถวท้ายไปหน้าใหม่ทีละแถวจนพอ

### 6.3 กระดาษ A4

```css
.docsheet {
  /* ★ height ไม่ใช่ min-height — หนึ่ง .docsheet = หนึ่งหน้า A4 เป๊ะ ห้ามยืด */
  width: 210mm; height: 297mm; padding: 14mm; overflow: hidden;
  background:#fff; color:#111; display:flex; flex-direction:column;
  font-size: var(--doc-fs, 10px);   /* ขนาดฐาน ตั้งค่าได้ต่อบริษัท */
}
```
- **ขนาดย่อยทุกตัวข้างในเป็น `em` ของค่าฐาน** ปรับตัวเดียวขยับทั้งใบพร้อมกัน
- ถ้าเขียนเป็น px ตายตัว จะต้องไล่แก้กว่าสิบจุดทุกครั้งที่เปลี่ยนขนาด และสัดส่วนจะเพี้ยน
- **CSS ทุกกฎต้อง scope ใต้ `.docsheet`** เพราะแผ่นนี้อยู่ในหน้าแอปจริง
  selector ลอย ๆ อย่าง `.note` `.sum` `.ttl` จะชนคลาสของแอปทันที

### 6.4 ห้ามเปิดหน้าต่างใหม่จาก callback

> ⚠️ **บทเรียนราคาแพง:** เรียก `window.open()` ใน callback ของ API
> ตอนนั้น user activation จากการคลิกปุ่มหมดอายุไปแล้ว เบราว์เซอร์ถือว่าเป็นป๊อปอัพที่เว็บเปิดเอง
> **แล้วบล็อกทิ้งทุกครั้ง** (ยิ่งแอปอยู่ใน iframe ยิ่งเข้มกว่าปกติ)

**วิธีที่ใช้ได้จริง:**
1. กางเอกสารเป็น **แผ่นพรีวิวทับอยู่บนแอป** แล้วให้ผู้ใช้กดปุ่มพิมพ์เอง → `window.print()` เกิดจากการคลิกจริงเสมอ
2. มีทางออกสำรอง **"เปิดในแท็บใหม่" เป็นลิงก์ `<a href>`** ที่ผู้ใช้คลิกเอง (คลิกลิงก์นับเป็น user activation)
   สร้างไฟล์ด้วย `URL.createObjectURL(new Blob([...], {type:'text/html'}))`
   **ไฟล์ที่เปิดแท็บใหม่ต้องมี CSS ของตัวเองติดไปด้วย** ไม่งั้นหน้าตาแตก

ผลพลอยได้: ผู้ใช้ได้ตรวจเอกสารก่อนพิมพ์ และสั่งพิมพ์ซ้ำหลายใบติดกันได้

### 6.5 ส่งออกเป็น .xlsx จริง ไม่ใช่ CSV

CSV มีปัญหาที่แก้ไม่ได้สองข้อ:
1. **Excel ตัด 0 นำหน้าทิ้ง** — รหัส `00012` กลายเป็น `12`
2. ภาษาไทยเพี้ยนถ้าลืม BOM และบางเครื่องก็ยังเพี้ยนอยู่ดี

```js
// บังคับให้ทุกช่องเป็นข้อความ (t:'s') — รหัสจึงไม่ถูกตีความเป็นตัวเลข
const ws = XLSX.utils.aoa_to_sheet([headers].concat(rows));
// ...ไล่ตั้ง cell.t = 's' ทุกช่อง
```
- ทำทั้งหมดที่ฝั่งเบราว์เซอร์ **ไม่ต้องวิ่งไปเซิร์ฟเวอร์ ไม่ต้องยุ่งกับไดรฟ์**
- โหลดไลบรารีแบบ lazy (ตอนใช้ครั้งแรก) ไม่ใช่โหลดทุกครั้งที่เปิดแอป
- **เตรียมไฟล์ให้เสร็จก่อนค่อยโชว์ปุ่มดาวน์โหลด** ไม่ใช่โชว์ปุ่มไว้ก่อนแล้วกดแล้วไม่มีอะไรเกิดขึ้น

ถ้าจำเป็นต้องใช้ CSV จริง ๆ ให้ใส่ BOM (`﻿`) เสมอ

### 6.6 เอกสารตัวจริง

```js
{
  docNo, title, subLabel, dateStr,
  metaLeft: [['ซัพพลายเออร์','...'], ['รับเข้าคลัง','...']],  // ซ้าย = ข้อมูลของงาน
  note, signers: ['ผู้ส่งของ','ผู้ตรวจรับ',...],              // ขวา = เลขที่/วันที่
  showCost, showDiscount, totalLabel, extraTotals,
  lines: [{ itemCode, name, qty, unit, unitCost, lineTotal }]
}
```

**ชุดช่องลงชื่อเดินตามลำดับงานจริงของเอกสารแต่ละชนิด** ไม่ใช่ชุดเดียวใช้ทุกใบ:
```
ใบโอน      ผู้สั่งโอน · ผู้อนุมัติ · ผู้จัดส่ง · ผู้รับของ
ใบรับสินค้า ผู้ส่งของ · ผู้ตรวจรับ · ผู้รับเข้าคลัง · ผู้อนุมัติ
ใบจ่ายออก   ผู้ขอเบิก · ผู้อนุมัติ · ผู้จ่ายของ · ผู้รับของ
            ↑ ของออกโดยไม่มีใบสั่งซื้อ/ใบขายเป็นต้นเรื่อง ถ้าไม่มีทั้งคนขอและคนอนุมัติก็สอบกลับไม่ได้
```

**ปุ่มพิมพ์ต่อใบในตาราง Journal** — ทุกเอกสารต้องพิมพ์ซ้ำได้ตลอด เผื่อใบเดิมหาย/เปื้อน
หรือต้องแนบไปกับเอกสารตั้งเบิก

### 6.7 ระบบเลขที่เอกสาร

```
doc_number_series : company_id, doc_type, prefix, separator, date_format,
                    digit_padding, per_branch, reset_cycle, is_active
doc_number_counters: ตัวนับแยกตาม series × ช่วงที่รีเซ็ต
```
- ตั้งค่าได้เองผ่านหน้าจอ (ผู้ดูแลระบบสูงสุดเท่านั้น) ไม่ใช่ฮาร์ดโค้ดในโปรแกรม
- แยกสองฟังก์ชันให้ขาด:
  - `getNextDocNumber()` **กินเลขจริง** → เรียกได้เฉพาะตอนกำลังบันทึกเอกสารจริงเท่านั้น
  - `previewNextDocNumber()` **ดูเฉย ๆ ไม่กินเลข** → ใช้กับหน้าจอที่โชว์ตัวอย่างเลขถัดไป
- **ห้ามสร้างเลขเอกสารด้วยการต่อสตริงเอง** สำหรับอะไรก็ตามที่ผู้ใช้เห็นว่าเป็น "เลขที่เอกสาร"

## 7. การคลังสินค้า

### 7.1 โครงสร้างสถานที่

```
company (บริษัท)
  └── branch (สาขา)
        └── warehouse (คลัง — type: stockroom / staging / ...)
```
- **ยอดสต็อกนับที่ระดับคลัง** ไม่ใช่ระดับสาขา (`branch_stock` มี `warehouse_id`)
- ทุกสาขาต้องมี "คลังหลัก" (`stockroom`) เป็นค่าตั้งต้นเมื่อผู้ใช้ไม่ได้เลือกคลัง
- **ถ้าหาคลังหลักไม่เจอ ต้องหยุดตั้งแต่ก่อนแตะข้อมูลใด ๆ** ไม่ใช่ทำไปครึ่งทางแล้วค่อยพัง
- แถวเก่าก่อนมีระบบหลายคลัง (`warehouse_id` ว่าง) เป็น bucket ของตัวเอง **ตั้งใจไม่ merge อัตโนมัติ**

### 7.2 ทางเข้า–ทางออกของสต็อก

**กติกาสำคัญที่สุดของทั้งระบบ: ของเข้าสต็อกได้ทางเดียว**

```
เข้า:  createGoodsReceipt()  ← ทางเดียวเท่านั้น ออกเลขที่เอกสารเสมอ
       (ยอดยกมาตั้งต้นเป็นข้อยกเว้นที่ตั้งใจ — เป็นการประกาศ ไม่ใช่การรับของ)
ออก:  createStockIssue()     ← จ่ายออกที่ไม่ใช่การขาย
       setSalesOrderStatus() ← ขายออก
ย้าย:  createTransfer()      ← ข้ามสาขา (มีขั้นรับปลายทาง)
       createWarehouseMove() ← ภายในสาขา (เกิดสองแถวเสมอ)
ปรับ:  submitStockCount()    ← ตรวจนับแล้วปรับให้ตรงของจริง
```

**ห้ามเพิ่ม "ทางลัดรับของ" เด็ดขาด** ไม่ว่าจะอ้างว่าเร็วกว่าแค่ไหน
ประเด็นทั้งหมดของระบบคือ **ทุกหน่วยที่เพิ่มเข้าสต็อกต้องสาวกลับไปหาเอกสารที่มีเลขและวันที่ได้**

การนำเข้าไฟล์จำนวนมากก็ต้องเดินผ่านทางเดิม — รวมทุกแถวเป็นเอกสารใบเดียวแล้วเรียกฟังก์ชันเดิม
ไม่ใช่เขียน `branch_stock` ตรง ๆ เพราะ "มันเยอะ"

### 7.3 ตรวจนับ

```js
diff = countedQty − systemQty
// เขียนแถวลง stock_counts เสมอ (ทั้งที่ต่างและไม่ต่าง — เป็นหลักฐานว่านับแล้ว)
// ถ้า diff ≠ 0 → ปรับสต็อก + ลงบัญชีรายการเป็น count_adjustment
```
ยอดระบบที่เอามาเทียบต้องเป็น **ยอดของคลังที่กำลังนับ** ไม่ใช่ยอดรวมทั้งสาขา
(หนึ่งสาขามีหลายคลังแล้ว สองตัวนี้ไม่เท่ากันอีกต่อไป)

### 7.4 นำเข้าข้อมูลจากไฟล์

**parse ที่ฝั่ง client เสมอ ไม่ส่งไฟล์ดิบไปหลังบ้าน**
```
เลือกไฟล์ → อ่านด้วย FileReader + SheetJS → จับคู่กับสินค้าในระบบ
→ แสดงตารางตรวจสอบ → ผู้ใช้ยืนยัน → ส่งเฉพาะ JSON ที่ parse แล้ว
```

**การจับคู่คอลัมน์ — ไล่ตามลำดับ "คำค้น" ไม่ใช่ลำดับคอลัมน์:**
```js
function findCol(keys, taken){
  for (const k of keys)               // วนคำค้นเป็นวงนอก
    for (let i=0; i<header.length; i++){
      if (taken && taken.includes(i)) continue;   // กันคอลัมน์เดียวถูกจับสองหน้าที่
      if (header[i].includes(k)) return i;
    }
  return -1;
}
```
> ⚠️ ถ้าวนคอลัมน์เป็นวงนอก หัวตารางอย่าง **"รหัสสินค้า" จะไปคว้าช่อง "ชื่อ" ด้วย** เพราะมีคำว่า "สินค้า" อยู่ในนั้น
> เจอจริงกับแบบฟอร์มที่ระบบสร้างเอง — แจกฟอร์มออกไปแล้วนำเข้ากลับไม่ได้

**ตารางตรวจสอบก่อนบันทึกต้องบอกให้ครบ:** แถวไหนจะเพิ่ม แถวไหนจะลด แถวไหนเท่าเดิม
และ **แถวไหนจับคู่ไม่ได้** (สีเตือน + บอกให้ไปถามก่อน อย่าเพิ่งบันทึก)

**แบบฟอร์มต้นแบบ** ให้ดาวน์โหลดได้ พร้อมรายชื่อสินค้าครบแล้ว เหลือแค่กรอกตัวเลข
— และ **อย่าใส่ "ยอดในระบบ" ลงในแบบฟอร์ม** เพราะคนจะลอกตามแทนที่จะไปนับของจริง

### 7.5 ถอนการนำเข้าได้

การนำเข้ายอดขายจากแพลตฟอร์มต้อง **ถอนคืนได้ทั้งชุด** (`import_undo` คืนสต็อกกลับ)
เพราะการนำเข้าผิดไฟล์/ผิดงวดเกิดขึ้นจริง และการไล่ลบทีละรายการด้วยมือคือหายนะ

## 8. กับดักที่เจอมาแล้วจริง

รวมไว้ที่เดียวเพื่อให้โปรเจกต์ใหม่ไม่ต้องเจ็บซ้ำ

| # | อาการ | สาเหตุจริง | วิธีกัน |
|---|---|---|---|
| 1 | เมนูย่อยไม่ยอมเปิด / แผงลอยกระพริบ | `mousemove` bubble ขึ้น parent แล้วไปฆ่า timer ของลูก | เช็คความสัมพันธ์สองทาง `b.contains(keep) \|\| keep.contains(b)` |
| 2 | หลังบ้านสำเร็จ log ว่า OK แต่หน้าจอ error | Date object ซ้อนใน response ทำให้ deserialize พัง | ทุกฟิลด์เวลาผ่าน `safeDateStr()` |
| 3 | รายการเรียงมั่ว | sort ด้วย `String(date)` ได้ลำดับตามชื่อวัน | sort ด้วยสตริงวันที่ที่ format แล้ว |
| 4 | แก้ไข/ลบพังทั้งระบบหลัง rename | find-and-replace ไปโดน `payload.id` | grep `payload\.` ไล่ดูก่อนทุกครั้ง |
| 5 | กดปุ่มรัวแล้วได้ข้อมูลซ้ำ | ไม่มีตัวกันที่จุดคอขวด | กันที่ `callApi()` ด้วย `MUTATING_ACTIONS` |
| 6 | เปิดหน้าต่างพิมพ์ไม่ขึ้น | `window.open()` ใน callback ถูกบล็อก | กางแผ่นพรีวิวในแอป + ลิงก์ให้กดเอง |
| 7 | ข้อมูลหายจากกระดาษเงียบ ๆ | เดาจำนวนแถวต่อหน้า + กระดาษ `overflow:hidden` | วัดความสูงจริงด้วยกล่องวัด A4 |
| 8 | Excel ตัด 0 นำหน้ารหัสทิ้ง | ส่งออกเป็น CSV | ส่งออก .xlsx และบังคับทุกช่องเป็นข้อความ |
| 9 | `12.299999999999999` โผล่บนจอ | ไม่ปัดก่อนแสดง | `Math.round(n*1000)/1000` ก่อน format |
| 10 | เขียนข้อมูลลงผิดคอลัมน์ | append ด้วย array ตำแหน่งคงที่ ทั้งที่ตารางเคยเติมคอลัมน์ทีหลัง | map ตาม header จริงเสมอ |
| 11 | สองคนคนละ role เห็นสิทธิ์ของกันและกัน | สิทธิ์ไหลผ่านแคชที่แยกตามสาขา | คำนวณสิทธิ์ใหม่หลังดึงแคชเสมอ |
| 12 | ยอดยกมาเพี้ยนหลังมีคนบันทึกย้อนหลัง | เก็บยอดตั้งต้นเป็นผลต่าง | เก็บเป็นค่าสัมบูรณ์ในตารางของตัวเอง |
| 13 | ย้อนดูเดือนก่อนแล้วได้ตัวเลขของเดือนหน้า | ใช้ค่าประกาศกับงวดที่เริ่มก่อนวันประกาศ | ค่าประกาศมีผลตั้งแต่วันที่ประกาศเป็นต้นไปเท่านั้น |
| 14 | ทั้งหน้าจอกดอะไรไม่ได้เลย | quote หลุดตัวเดียวใน `onclick` ที่ต่อสตริง | `node --check` บล็อก `<script>` ทุกครั้งก่อน deploy |
| 15 | นำเข้าไฟล์ช้ามากจนใช้ไม่ได้ | เขียนทีละแถวในลูป (2 ตาราง × N รายการ) | รวมเป็น array แล้วเขียนรวดเดียว |

### กับดักเชิงวิธีทำงาน (สำคัญไม่แพ้กัน)

> **"เร็วไป/กระพริบ/ไม่นิ่ง" = ต้องวัด ไม่ใช่ปรับค่า**
> เคยไล่ปรับค่าหน่วงเวลาอยู่ 5 รอบโดยไม่หาย พอ hook ฟังก์ชันที่เปิด/ปิดเมนูแล้วอ่าน call stack จริง
> เจอต้นเหตุในรอบเดียว — **อาการ UI ที่ปรับค่าแล้วไม่หาย แปลว่าเดาสาเหตุผิด ไม่ใช่ปรับน้อยไป**

> **เทสต์ต้องตรวจจากสิ่งที่ผู้ใช้เห็น**
> เทสต์ที่ดูแต่ตัวแปรภายในเคยปล่อยบั๊กเดิมหลุดสามรอบติด
> UI ต้องตรวจจาก **HTML ที่วาดออกมาจริง** และเอกสารต้องตรวจจาก **แผ่นกระดาษที่สร้างจริง**

> **ก่อน `rm -f *.js` เช็ค `pwd` เสมอ** — เคยลบไฟล์เทสต์ทิ้งเพราะรันผิดโฟลเดอร์
> ใช้ `rm -f ./*.js` และตรวจตำแหน่งก่อนทุกครั้ง

## 9. เช็คลิสต์สำหรับโปรเจกต์ใหม่

### วางรากฐาน (ทำก่อนเขียนฟีเจอร์แรก)
- [ ] แยกโปรเจกต์หน้าบ้าน–หลังบ้านคนละ deployment ตั้งแต่วันแรก
- [ ] router ตัวเดียว + สัญญา `(user, payload) → {success, ...}`
- [ ] ชั้นเข้าถึงข้อมูลบาง ๆ (อ่าน/เขียน/แก้/ออกเลข id) เป็นทางผ่านเดียว
- [ ] ระบบเติมคอลัมน์อัตโนมัติที่รันซ้ำได้โดยไม่พัง
- [ ] ตัวช่วยจัดการวันที่ (`safeDateStr` / `safeDateOnly`) และใช้ให้ครบทุกที่
- [ ] RBAC แบบ โมดูล × (ดู|แก้ไข) + ทางออกฉุกเฉินของผู้ดูแลสูงสุด
- [ ] design token ครบชุด รวมสีความหมายที่แยกจากสีแบรนด์

### โมเดลข้อมูล
- [ ] ตารางสินค้าเดียวแยกด้วยชนิด + id ลำดับเดียวทั้งระบบ
- [ ] `item_code` เป็นรหัสธุรกิจที่ใช้กับทุกชนิด (พร้อมบังคับ unique ถ้าทำได้)
- [ ] แยก `record_id` (ภายใน) / `item_code` (ธุรกิจ) / `id` (สัญญา API)
- [ ] `branch_stock` + `stock_movements` ที่กระทบยอดกันได้เสมอ
- [ ] แยก `created_at` ออกจาก `transaction_date`
- [ ] ตารางยอดยกมา + ตารางประวัติแบบเขียนอย่างเดียว

### การทำงานของคลัง
- [ ] ทางเข้าสต็อกทางเดียว ออกเลขที่เอกสารเสมอ
- [ ] ระบบเลขที่เอกสารที่ตั้งค่าได้ + แยกฟังก์ชัน "กินเลข" กับ "ดูเฉย ๆ"
- [ ] เขียนข้อมูลแบบ batch สำหรับงานนำเข้า
- [ ] ถอนการนำเข้าได้ทั้งชุด
- [ ] ตรวจนับเทียบกับยอดของคลังที่นับ ไม่ใช่ยอดรวมสาขา

### หน้าจอและเอกสาร
- [ ] กันกดซ้ำที่จุดคอขวดเดียว
- [ ] แถบงานเบื้องหลังสำหรับงานที่ใช้เวลา (อย่าขังผู้ใช้ไว้หน้าโมดัล)
- [ ] เครื่องพิมพ์กลาง: เอกสารทีละใบ + รายงานตาราง
- [ ] แบ่งหน้าด้วยการวัดความสูงจริง
- [ ] ส่งออก .xlsx โดยบังคับทุกช่องเป็นข้อความ
- [ ] ไม่มี `window.open()` ใน callback ที่ไหนเลย

### วินัย
- [ ] ตรวจ syntax ของบล็อกสคริปต์ทุกครั้งก่อน deploy
- [ ] เทสต์ตรวจจาก HTML/กระดาษที่วาดจริง ไม่ใช่จากตัวแปรภายใน
- [ ] อาการ UI ที่ปรับค่าแล้วไม่หาย → หยุดปรับ ไปวัดของจริง
- [ ] คู่มือผู้ใช้อยู่ในแอป ไม่ใช่ไฟล์ที่ต้องไปตามหา

## ภาคผนวก — ขนาดของระบบอ้างอิง

ตัวเลข ณ วันที่เขียนเอกสารนี้ เพื่อให้ประเมินขนาดงานได้:

| รายการ | จำนวน |
|---|---|
| ตารางข้อมูล | 35 |
| คำสั่งงาน (action) | 83 |
| โมดูลสิทธิ์ | 19 × 2 ระดับ |
| บรรทัดโค้ดรวม | ~21,000 |
| ชุดทดสอบอัตโนมัติ | 300+ ข้อ |

**แพลตฟอร์ม:** Google Apps Script (V8) + Google Sheets + LINE LIFF
ไม่มีขั้นตอน build ไม่มี npm — ทุกอย่างเป็นไฟล์ HTML/JS ที่เสิร์ฟตรง และไลบรารีโหลดจาก CDN

**ข้อจำกัดที่ต้องรู้ก่อนเลือกแพลตฟอร์มนี้:**
- แต่ละคำขอใช้เวลาราว **2–3 วินาที** ไม่ว่าจะทำอะไร → ต้องออกแบบให้ยิงน้อยครั้งที่สุด
  (รวมหลายอย่างไว้ในคำขอเดียว เช่น "ใครคือคุณ + ข้อมูลทั้งหมด" ในรอบเดียวตอนเปิดแอป)
- **Sheets ไม่มีระบบล็อกแถว** — อ่าน-แก้-เขียนมีช่องว่างให้ชนกันได้
  ยอมรับได้ที่ทีมขนาดเล็กเขียนไม่พร้อมกัน แต่ต้องมีแผนย้ายฐานข้อมูลไว้ล่วงหน้า
- เหมาะกับ **ทีมเล็กถึงกลาง ข้อมูลระดับหมื่นแถว** ถ้าเกินกว่านี้ให้ยกโมเดลข้อมูลกับตรรกะในเอกสารนี้
  ไปวางบนฐานข้อมูลจริงแทน — **ส่วนที่มีค่าที่สุดของเอกสารนี้คือหลักการ ไม่ใช่โค้ด GAS**
